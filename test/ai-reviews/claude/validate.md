# Fable 5.1 review — Triauth.validate

## Summary

`Triauth.validate` is a synchronous format check over five inputs, the identifier, the device name, the bare group name, the lookup code and the device tag. It performs no DNS lookup, reads no clock or randomness, keeps no state, writes no log line and never echoes an input back in a message. Every grammar it applies is the grammar the flows apply. `Validator.validateIdentifier` is the gate of stage 1 and stage 3 of every challenge-response flow, of the `Identity` constructor behind `check` and `whois`, of `Signature.generate`, of the signature envelope parser and of the actor part of a composite device tag in `check`. `Validator.validateDeviceName` admits the device names of published key records, `Validator.validateGroupName` admits the names of a published `groups` record, `Validator.validateLookupCode` is the `whois` gate, and its `Helpers.isLookupCode` rule is the one `IdentityDomain.derive` and `Signature.verify` apply to a lookup code before it keys a derivation. The device-tag grammar accepts exactly the tags a result can carry, a 43-character canonical base64url digest with an optional `~` and a 16-character lookup code, or three such parts around a canonical actor identifier, which is the string `Signature.verify` composes and `check` decomposes. A pre-check with `validate` therefore predicts the format verdict of the method the value is headed for, and no flow depends on the caller running it. `validate` is stricter than `check` in one place only. `check` ignores a third `~` piece of a tag component, while `validate` rejects it, and no result ever carries one.

The accepted identifier grammar is a lowercase ASCII subset with exactly one `@` sign, a name part of at most 63 characters without consecutive or edge dots and hyphens, LDH domain labels of at most 63 characters, at least two labels, no Punycode label, no numeric final label and no trailing dot, within 120 bytes. The underscore of the `_at` marker is outside both grammars, so no two accepted identifiers address the same identity records. Every non-ASCII character, including Cyrillic look-alikes, zero-width and bidirectional controls, NBSP, BOM, C0 controls, DEL and lone surrogates, fails the ASCII grammar of the name part or of the domain, and the lowercase test compares against `toLowerCase()` instead of folding, so the Kelvin sign and the Turkish dotted I are rejected rather than mapped onto ASCII. The name grammar shared by device names and group names is lowercase alphanumerics joined by single hyphens within 20 bytes, which also keeps the `xn--` marker out. A lookup code is 16 uppercase ASCII letters and digits, never trimmed, folded or stripped of display hyphens. A device tag component must decode as canonical base64url, so a digest with payload in the unused bits of its last character, a padded spelling or a standard-base64 character is rejected.

The argument guards fail closed for every JSON-shaped input, including own `__proto__` and `constructor` keys, `String` objects, symbol-keyed and inherited properties, and a typo or an undefined value in the global `Triauth.config` is reported as `invalid_config`. A getter whose value changes between the guard read and the validation read ends in `invalid`. Each call returns fresh result objects with static table messages, and `valid` is `true` exactly when `errors` is empty (verified over a corpus at e464988). The README and the JSDoc both state that `{valid: true}` confirms the format only and is not output sanitization. An accepted-length input costs 1.3 to 2.2 microseconds per call, and an oversized identifier, device name or group name is rejected in about 10 microseconds before any pattern scan. The device-tag path is the exception, see VALID-004. The unit tests, the config-guard test and the validate JSON suite pass at e464988. This scope is safe to use in mission-critical production systems. The findings are one low and two informational.

## Findings

### [VALID-002] [info] Exotic argument objects make validate throw instead of returning a result
**Location:** `src/api/validation.js:92`
**Description:** `validate` has no exception boundary. The argument guards call `Array.isArray` and `Object.keys` on the caller's object and read its properties, and `Helpers.mergeConfig` copies the override with `Object.assign`. For a revoked Proxy, a Proxy with a throwing `ownKeys` trap, or an object whose `identifier` accessor throws, the exception propagates to the caller instead of a `{valid: false}` result. The same holds for the config argument, where a throwing `ownKeys` trap or a throwing accessor on the override propagates. The async API methods normalize every throw into `{error: {code: 'internal_error'}}`, so `validate` is the one public method that can throw. No JSON-shaped input reaches this path. `undefined`, `null`, strings, numbers, arrays, `String` objects, frozen objects, null-prototype objects such as a query-string parser produces, symbol-keyed objects, objects with own `__proto__` or `constructor` keys, objects with an inherited `identifier` and a getter that returns a different value on its second read all return a result (verified at e464988). A throw is itself a fail-closed outcome for a request handler, so the exposure is the availability of one request, under objects the caller constructed.
**Recommendation:** State in the JSDoc and the README that `validate` returns a `{valid, errors}` result for plain data objects and throws for accessor or Proxy objects, so the contract is explicit.

### [VALID-003] [info] A config override with an own `__proto__` key passes the `invalid_config` guard
**Location:** `src/api/validation.js:108` (the merge is `src/helpers.js:1047`)
**Description:** The guard inspects the merged copy that `Helpers.mergeConfig` builds with `Object.assign`. `Object.assign` writes an own `__proto__` key of the override through the `__proto__` setter that the fresh copy inherits, so the value becomes the prototype of the copy instead of an own key. `Object.keys` on the copy then lists the global keys only, and the guard passes. `Triauth.validate({identifier: 'john@example.com'}, JSON.parse('{"__proto__": {"evil": 1}}'))` returns `{valid: true}`, where every other unknown key, an own `constructor` key included, returns `invalid_config` (verified at e464988). The global `Object.prototype` stays untouched, and the copy is local to the call. A non-object override such as `42`, `true` or `null` passes the guard for the same reason, `Object.assign` copies nothing from it, while a string or an array is reported as `invalid_config` through its index keys. `validate` reads nothing from the config after the guard, so its result is unaffected. Every known key is an own property of the global config and is copied first, so a prototype injected this way shadows no setting in the methods that do read the config. The override is integrator-supplied input, which the trust model places inside the trusted code. The exposure is one undocumented exception to the rule that an unknown override key is rejected, in the one helper that backs the guard of every public method.
**Recommendation:** Build the merged config with object spread, `{...config, ...overrides}`, which copies an own `__proto__` key as an own data property, so the existing guard reports it as `invalid_config`. Add the case to `test/internals/test_config.js`.

### [VALID-004] [low] The device-tag check splits the whole input before any size gate
**Location:** `src/validator.js:523` (the component split is `src/validator.js:543`)
**Description:** `Validator.validateDeviceTag` splits the entire string on `:` and then each component on `~` before any length comparison, so its cost grows with the input even though no well-formed tag is longer than 242 characters (two 60-character tag components and a 120-byte actor identifier around two colons). The identifier, device name and group name paths compare `.length` against their cap first and reject an 8 MiB input in about 10 microseconds. The device-tag path takes 3.6 ms for 100 KiB of tildes, 33 ms for 1 MiB and 286 ms for 8 MiB, and the split of 8 MiB of colons allocates a transient array of 8 million entries, about 37 MB of heap (measured at e464988). The cost is linear, nothing throws, and the verdict is the correct `invalid_device_tag`, so a stall is bounded by the request body size the integrator's HTTP layer admits, about 4 ms under a typical 100 KB body limit. The exposure is the availability of a synchronous call the README describes as fast, on an input an unauthenticated client controls when `validate` fronts a `check` endpoint. The same split-before-size shape appears in `Validator.validateSessionKey` (`src/validator.js:440`, 79 ms for 8 MiB of colons) and in the device-tag parse of `check` (`src/api/authentication.js:342`), which belong to other scopes.
**Recommendation:** Reject a device tag longer than the longest well-formed one, 242 characters, before the split, with an explicit `.length` test on the validator's own string gate, the pattern the identifier and name paths use. Derive the cap from the constituents (two tag components of 43 + 1 + 16 characters, the identifier byte size and two delimiters) or pin it as a `LIMITS` entry, and add an 8 MiB case next to the existing oversized-identifier test. Apply the same length gate to `validateSessionKey` (at most 253 + 1 + 43 characters) in the same pass.
