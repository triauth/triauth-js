# Fable 5.1 review — Triauth.whois

## Summary

`Triauth.whois` is a read-only lookup. It validates its arguments before any DNS traffic (102 for an unknown option key or a bare string, 103 for an unknown config key, 101 for a missing identifier or a malformed lookup code, 21x for a malformed identifier), resolves the domain's `triauth` record and then the identity records, and returns a deep copy of what it read. The lookup code is consumed only as the HMAC key of the private-mode label derivation. It is never echoed in a result and never logged at any level. Record parsing is linear in the answer size and fails closed per record family, with caps on devices, keys per device, grants, groups, and profile entries. Under private mode the commit record binds an answer to the derivation that was performed, so a wrong code and a label collision both resolve to `status: 0`, and a lookup without a code performs no identity query at all. A DNS failure surfaces as error 110 instead of a false "does not exist". The `secure` flag is the AND of the endpoint record and every well-formed identity record, and it is false when no resolver reports a DNSSEC status. Prototype-poisoning keys are dropped at the record parser, and device names, group names, record keys, and option keys are confined to closed grammars. A stub-resolver probe at this commit confirms each of these statements and each finding below.

Two low findings. `config.requireSecure` has no effect on whois, so a caller who opts in receives non-DNSSEC results as `status: 1`. The README rate-limit guidance does not cover whois, although whois resolves two caller-chosen names per call with no session key. Five informational notes concern the meaning of `status: 1`, result fields that return DNS text verbatim, debug logging under private mode, the private-mode identity domain as a handle to the records, and the difference between a whois device tag and a sign-in device tag.

From the whois perspective the library is safe to use in mission-critical production systems. The low findings are closed by a one-line gate or by documentation, and no finding lets a caller authenticate or act as another identity.

## Findings

### [WHOIS-001] [low] `config.requireSecure` has no effect on whois
**Location:** `src/api/identity.js:215-226` (compare `src/api/authentication.js:421-422` and `src/api/signing.js:714-717`, both through `src/challenge_response_flow.js:341-345`)
**Description:** The status 1 result carries `identity.secure`, and `config.requireSecure` is never read on the whois path. A stub-resolver probe at this commit returns `status: 1` with `secure: false` under `{requireSecure: true}` for an unsigned endpoint record and an unsigned identity answer. `Triauth.check` on the same device under the same config returns error 404. The error 103 guard cannot catch this because the key is recognized. The config comment at `src/config.js:41-47`, the README default-configuration block at `README.md:1813-1816`, and the Best Practices bullet at `README.md:2031` name the gated methods and do not say that whois is exempt, so an operator who opts in has to read the lists closely to learn that the one method that lists key material is not covered. The exposed data is the device list with its key material, the delegation grants, and the group claims. An operator dashboard built on whois shows attacker-published devices or grants from a poisoned unsigned zone with no error. The whois.json suite has no requireSecure vector, while auth, check, ping, verify, sign, stamp, and attest each carry one.
**Recommendation:** Call `ChallengeResponseFlow.assertSecure(identity.secure, config)` before the status 1 return, and leave the status 0 and -1 results ungated like the revoked path of check. If the exemption is intended, state it in the `requireSecure` comment in `src/config.js`, in the README default-configuration block, and in the whois JSDoc. Pin the chosen behaviour with a whois.json vector.

### [WHOIS-002] [low] Rate-limit guidance does not cover whois
**Location:** `README.md:2038-2039`, `src/api/identity.js:180-194`
**Description:** One whois call resolves two caller-chosen names, the identifier's domain and then the identity domain, through every configured resolver. The default MultiResolver sends up to six outbound queries per call before retries, and the answer costs one HMAC plus up to about sixty SHA-256 digests for device and grant tags. whois takes an arbitrary identifier and needs no session key, no challenge, and no session, so it is the method most likely to sit behind an unauthenticated "look up this address" endpoint. The README bullet on rate limiting covers only stage 1 and stage 3 of the challenge-response flows. With NodeDns in the resolver set, every call also makes the integrator's system resolver query a zone of the attacker's choice, which shows that resolver's egress address to the zone's authoritative server.
**Recommendation:** Extend the bullet to whois and check. Refer to the Caching DNS responses section (`README.md:1915`) for repeated lookups of the same identifier.

### [WHOIS-003] [info] `status: 1` means one well-formed record, not a usable identity
**Location:** `src/identity.js:293`, `src/identity_keys.js:137-138`, `README.md:754-757`, `README.md:846`
**Description:** `Identity.resolve` reports success when the identity answer contains at least one record that parses as a key followed by a value, whatever the key. A wildcard record such as `*._at.example.com TXT "hello world"`, or any stray TXT record at the identity's name, makes an identifier of a public-mode domain report `status: 1` with `devices: []`, `publicProfile: {}`, `groups: []`, and `includes: []`. A stub-resolver probe at this commit confirms this. Private mode is not affected because the commit record is required (`src/identity.js:274-281`). The `devices` list is syntactic in the same way. A key value is checked for length and the base64url alphabet only, so a record such as `key laptop[1/1]:AAAA type=es256` is listed as a complete device with a device tag, although no verifier can load the value. The README describes `1` as "the identifier exists". An integrator who uses whois to decide whether an address can sign in with Triauth, or to pre-provision an account, reads existence where there is none. Sign-in itself is unaffected because no usable keys are published.
**Recommendation:** Document that `1` means at least one well-formed identity record is published and that `devices` can be empty or carry keys that no verifier accepts, and tell callers to test `devices.length` when they need to know that an identifier can sign in. Alternatively, count only recognized record families toward existence. The whois.json vector for an uppercase `NAME` record (`test/fixtures/json/whois.json:1032`) pins the current rule, so a change needs that vector updated in lockstep.

### [WHOIS-004] [info] Result fields beyond `publicProfile` return DNS text verbatim
**Location:** `src/api/identity.js:186-192`, `src/api/identity.js:206`, `src/api/identity.js:213`, `src/authentication_endpoint.js:146-153`, `src/resolvers/base.js:130`, `README.md:848-854`, `README.md:2050-2051`
**Description:** Three result areas hand DNS text to the caller as published. `authenticationEndpoint.options` is the endpoint record's option map with no schema applied, so unknown keys are retained and their values are bounded only by the size of the TXT answer, because the record parser accepts option values of any length. `devices[].keys[].options` and `includes[].options` keep every `x-` option, whose values may contain the characters `<`, `>`, `"`, `'`, `&`, `/`, and `=`. A stub-resolver probe at this commit returns `color: "<b>x</b>"` and a 3000-character value on the endpoint, `x-note: "<img/src=x/onerror=alert(1)>"` on a device key, and `x-why: "<svg/onload=alert(2)>"` on a grant. The README whois table marks only `publicProfile` as raw text, and the Best Practices bullet names device key options but not endpoint options or include options. Only the domain owner can publish these values, so the exposure is a rendering concern for the integrator, not a cross-domain one. Record keys and option keys are confined to word characters, brackets, dots, and `@`, so only values carry such text.
**Recommendation:** Mark `authenticationEndpoint.options`, key `options`, and include `options` as raw text in the whois result table. Optionally bound endpoint option values at the record parser with the 255-byte Normal String limit that `x-` options get at the schema check, so one record cannot grow a result.

### [WHOIS-005] [info] Debug logging links a private-mode identifier to its derived label
**Location:** `src/identity_domain.js:189`, `src/identity.js:130`, `src/resolvers/base.js:79`, `src/identity_keys.js:152`, `README.md:1892-1894`
**Description:** At the debug level the resolution logs the identifier together with the derived identity domain, for example `Identity domain for identifier "john@example.com" is "_4GIBDU53B3._at.example.com"`, and logs raw key data on a tainting record. The Privacy Considerations section (`README.md:1988-1989`) explains that private mode keeps a third party who sees the label from linking it to an identifier without the lookup code. A debug log shipped to a shared log service stores that link for every lookup. The Logging warning names challenges, signatures, payloads, and key values as debug-level artifacts, and identifiers and device tags as info-level ones, but not this pairing. A probe at this commit with a capturing logger shows that the lookup code itself appears on no line at any level, and that the info level emits only the "Processing" and "Completed" lines for whois, so this concerns only integrators who turn debug logging on.
**Recommendation:** Name the identifier-to-label pairing in the Logging warning, or log the derived label without the identifier on that line.

### [WHOIS-006] [info] A private-mode `identityDomain` in the result is a handle to the records
**Location:** `src/api/identity.js:197`, `src/api/identity.js:218`, `README.md:849`, `README.md:2041-2043`
**Description:** Under `mode=private` the status 0 and status 1 results carry `identityDomain`, the code-derived label such as `_BLWJ2RAECC._at.example.com`. The lookup code is needed only to derive that label. The label itself addresses the records, so anyone who learns it reads the commit, key, profile, group, and include records from public DNS without the code. A probe at this commit confirms this with a bare TXT query for the returned label. The result also pairs the label with the identifier, which is the link that private mode withholds from third parties (`README.md:1988-1989`). The Best Practices bullet tells integrators to treat `deviceTag`, `lookupCode`, and `actorLookupCode` like the identifier and not to display them, but does not name `identityDomain` or `actorIdentityDomain`, and the whois result table shows a private-mode example with no such note. The same field appears on every sign-in, ping, attest, sign, stamp, and verify result. The caller already holds the lookup code, so this concerns results that are displayed, stored, or logged beyond the user they belong to. See WHOIS-005 for the same pairing at the debug log level.
**Recommendation:** Add `identityDomain` and `actorIdentityDomain` to the "Treat … like the identifier" bullet, or note in the whois result table that a private-mode identity domain reads the records without the lookup code and is handled like the code.

### [WHOIS-007] [info] A whois `deviceTag` is the bare device tag, not the sign-in `deviceTag`
**Location:** `src/api/identity.js:208`, `src/signature.js:377-378`, `src/api/authentication.js:342-343`, `README.md:853`, `README.md:497`
**Description:** whois returns the key group's tag as published. A sign-in result's `deviceTag` appends `~<lookupCode>` under private mode and is composite for a delegated sign-in (`<includeTag>:<actor>:<actorDeviceTag>`), and `Triauth.check` splits those forms before it matches. The authenticate result table documents the suffixed form with an example, and the whois table does not say which form it returns. An integrator who marks "this device" in a device list, or who builds a home-grown revocation check, by string-comparing a stored session `deviceTag` against the whois `devices` list never gets a match for a private-mode or delegated session. The mismatch fails closed, but a whois-based check also skips the `requireSecure` gate of WHOIS-001 and the grant and actor checks that `Triauth.check` performs for a delegated tag.
**Recommendation:** State in the whois result table that `deviceTag` is the bare device tag, equal to the part of a direct sign-in `deviceTag` before any `~`, and that for a delegated sign-in the first component matches `includes[].tag` of the subject while the device component matches a device of the actor. Point to `Triauth.check` for revocation.
