# Fable 5.1 review — Triauth.authenticate

## Summary

`Triauth.authenticate` verifies a stage-3 response along one path. `ChallengeResponseFlow.perform` opens the sealed response with the decryption key that is stored with the challenge. `verifyChallengeResponse` then runs the envelope through `Response.verify`, `MultiSignature.verify` and `Signature.verify`. The seal is HPKE in base mode with a fresh P-256 key pair for every challenge. A response therefore opens only with the challenge it was made for. Any change to it fails the AES-GCM tag before the first DNS query. The device signature covers the exact challenge bytes, with the encryption key inside them. It also covers the envelope type, the identifier, the actor, the `via` base URL, the device timestamp and the signed metadata. The verifier accepts exactly one envelope segment, and it pins the challenge type and the identifier before any DNS query. It checks the freshness windows of the challenge and of the signature. It checks the key `use` option, a complete key group, and the WebAuthn origin of the resolved authenticator. For a delegated sign-in it checks the grant with its flow and its service host. It checks the private-mode commitment, and it checks that the signed `via` equals the base URL of the challenge's callback URL. Every parse and constraint failure fails closed. A DNS failure is reported as the retryable error `dns_unavailable`, never as a false verdict. The error objects have string codes, with a `reason` on validation errors. The JSON parser admits only safe integers, well-formed strings and ASCII object keys, and it rejects the prototype-poisoning keys. The endpoint record parser keeps only the `mode`, `include` and `x-` options. The compressed P-256 key form that `es256` and `webauthn-es256` records accept is decoded with a field-prime bound, a curve check and a parity rule. I found no way to authenticate as an identifier without a signature from keys that its identity records publish or delegate to.

The headline concern is AUTH-001, which the founder accepted as by design on 2026-10-01. The open items are two low findings and five info notes. AUTH-002 is the resolution order of the delegated path. AUTH-009 is the session identifier of the README's Express example, which does not change across the sign-in. An attacker who plants a session cookie in the victim's browser therefore receives the victim's signed-in session. The info notes record the log content and the stage-1 redirect. They record replay protection as the application's duty. They record that the session key is a property of the seal and not of the signature. They record that a delegated sign-in authenticates the subject by default. The sealed response closes the response-injection form of login CSRF on its own. The Best Practices section and the Express example close the identifier-injection form with a same-origin check of the stage-1 request.

The library is safe to use in mission-critical production systems when the deployment follows the README. The stored challenge stays server-side, out of URLs and logs, and is invalidated after every attempt. The session key is stored with the server-side session, and the session identifier is renewed when the sign-in completes. Strict deployments set `config.requireSecure`. Both stages are rate limited, and the stage-1 endpoint accepts only requests that the application's own page made. This review is grounded on the trust model page, read from the triauth-www checkout, on the code and on the README. The full mocha suite passes on this tree with 2258 tests, 56 of them under `Triauth.authenticate`.

## Findings

### [AUTH-001] [medium] [reviewed] Stage 3 binds the response to the challenge's callback URL, not to the verifying application's
**Location:** `src/challenge_response_flow.js:210-216` (optional `callbackUrl` constraint), `src/challenge_response_flow.js:285` (`via` must equal the base URL of `challenge.data.cburl`), `src/api/authentication.js:228-247` (the result carries neither `via` nor `cburl`)
**Description:** The only site binding that the verifier enforces on its own is `getBaseUrl(challenge.data.cburl) === sig.via`. Both values come from the same source. The challenge supplies `cburl`, and the authenticator derives `via` from that same `cburl` before it signs. The verifier therefore proves that the response belongs to the challenge, not that the challenge belongs to the application that verifies it. The stage-3 `callbackUrl` option closes that gap, but it is optional, and the success result exposes neither `via` nor `cburl`, so an application cannot check the site binding after the fact.

This is a secure-default gap, not a bypass. When the challenge is held server-side, as the Best Practices require, it carries the application's own `cburl` and the binding is complete. When the challenge travels through the client, as in the README's browser example or in a single-page app whose API receives both `challenge` and `response` from the browser, a genuine response can be substituted across sites. An attacker runs an ordinary triauth sign-in on a site of their own. A victim signs in there, and the attacker's server receives a genuine (challenge, response) pair for the victim, with `cburl` and `via` naming the attacker's site. The attacker submits that pair to the target application. Every check passes, and the target signs the attacker in as the victim. This is the same class as the token substitution attacks on OAuth implicit flows, which audience checks close. The GET and HASH callback methods, documented as useful for client-side applications, make the client-held pattern likely in practice.
**Recommendation:** Require the application's `callbackUrl` in stage 3 of `authenticate` (and of the other challenge-response methods), so that `challengeObj.data.cburl` is always compared with a value the server controls. This is a code-only change with no wire impact. If the option stays optional, return `callbackUrl` (or `via`) on the success result so an application can pin it, and promote the stage-3 `callbackUrl` constraint from a side note to a Best Practices rule for every deployment where the challenge is not held server-side.
> **Human review (triauthor, 2026-10-01):** By design. The challenge is server-side state. Stage 3 verifies a response against the challenge the application itself issued and stored, so the callback URL in it is already the application's own. A client-side application cannot trust any verification it performs itself, whatever the library checks. A backend that needs proof of identity runs the flow on its own, or asks for a `stamp` or `sign` over a nonce it issued and verifies the result with `via` pinned. The README states both rules. Accepted.

### [AUTH-002] [low] Delegated path resolves and verifies the actor before the subject's grants are consulted
**Location:** `src/signature.js:313-357`
**Description:** For an envelope with a non-empty `actor` slot, `Signature.verify` resolves the actor's identity with two DNS queries on the actor's domain. It then verifies the crypto signatures against the actor's keys. Only then does it resolve the subject and search its grants. The `actor` slot is chosen by whoever submits the response, and it may be an identifier under any domain. A stage-3 request must first open under the challenge's key pair, so the sender needs the readable challenge of a stage-1 call. The party that started the flow receives that challenge in the `redirectUrl`, so this is no obstacle. The request then drives DNS lookups to an attacker-chosen domain and a full key-group verification before the subject's records, which decide the outcome, are read. This happens also when the subject publishes no grant at all, which is the common case. The outcome is still `verification_failed`. The cost is DNS egress, CPU, and a query that the attacker's name servers observe. The record limits bound the crypto cost. The attacker's zone can publish ten devices of five keys each, and an envelope can have ten signatures. One request then costs at most five hundred signature checks. Stage 1 already allows a lookup of an attacker-chosen domain through the identifier, so the gain for an attacker is small. The README's rate-limit guidance bounds the volume.
**Recommendation:** Resolve the subject first. If the subject publishes no grant whose `domainName` equals the actor's domain, return `false` before the actor is resolved. That test is a string comparison on parsed records, with no DNS query. Keep the grant match on the actor ref, the flow and the service host after the actor resolves. The order change alters no verdict, since both resolutions are required for a delegated success and either failure yields the same result.

### [AUTH-003] [info] Info and debug logs include device tags with lookup codes and the full verification result
**Location:** `src/api/authentication.js:218`, `src/challenge_response_flow.js:129`, `src/response.js:148`
**Description:** `authenticate` logs `deviceTag` at info level. Under `mode=private` that value includes the lookup code, and for a delegated sign-in also the actor's identifier. Stage 1 logs the identifier, the callback URL and the requested `ext` at info level. `Response.verify` logs the complete verification result at debug level, with the signed metadata, the lookup codes, the device tag and the public key values. Neither the session key nor the decryption key of the stored challenge is passed to the logger on any path I traced. The opened envelope is not logged either. The error path logs the thrown error as `cause` at info or warn level. None of the errors on the stage-3 path has a key or an envelope in its data. A JSON syntax error from a malformed stored challenge can quote a fragment of the decoded challenge, which has no secret in it. The default logger runs at the error level, so nothing is emitted out of the box. The Logging section of the README states that debug output contains sensitive protocol artifacts. It states that info output contains identifiers, callback URLs, `ext` options and device tags with lookup codes. It asks operators to review that output before it goes to a third party. The remaining exposure is an operator who raises the level on a shared log pipeline against that advice.
**Recommendation:** Keep the README warning. A cheaper safeguard is to redact the `~<lookupCode>` suffix of `deviceTag` in the info line of `authenticate`. The lookup code then appears only at debug level.

### [AUTH-004] [info] Stage 1 redirects to the host that the identifier's domain publishes
**Location:** `src/challenge_response_flow.js:158-177`, `src/authentication_endpoint.js:127-140`
**Description:** The `redirectUrl` is `https://<host>/auth.html#?challenge=...`, where `<host>` is the value of the `triauth` TXT record of the domain in the user-typed identifier. The host passes the domain-name grammar and nothing else. An application whose sign-in endpoint accepts the identifier from a GET parameter therefore acts as an open redirector. The target is any https host that a zone operator chooses. This is inherent to the protocol, in the same way as identity-provider discovery in federated sign-in. The README asks for a top-level navigation so that the user sees the authenticator's origin. The redirect happens in the browser, so the server never connects to that host. Stage 1 resolves only the endpoint record, never the identity records, so it does not reveal whether the identifier exists. The challenge travels readable in the URL fragment, so the authenticator page can read the identifier and the callback URL. The Privacy Considerations section of the README documents this.
**Recommendation:** Integrators start stage 1 from a POST form and protect it as the Best Practices section describes. The protection is a CSRF token or the `Sec-Fetch-Site` check of the Express example. They may show the authenticator host, the host part of `redirectUrl`, to the user before the redirect. No library change is required.

### [AUTH-005] [info] Verification is stateless, so replay protection is the application's duty
**Location:** `src/challenge_response_flow.js:305-312`, `src/response.js:113-127`, `src/config.js:71`
**Description:** A valid (challenge, response) pair verifies again on every call while the challenge `iat` is inside the `authTimeout` window. The signature `ts` must also be inside the client clock drift. The window is three minutes by default, widened by the server clock drift. The challenge nonce makes each challenge unique, but the library keeps no state and cannot reject a second presentation. Each presentation also yields the same session key, so a replayed response gives the application a second session with the key of the first. The README prescribes invalidation of the stored challenge after every attempt and a monotonic `issuedAt` check. AES-GCM detects any change to the sealed string, and an outsider cannot open or re-seal it. A second response string with different bytes can therefore come only from a party that has the plaintext envelope. Deduplication therefore keys on the challenge, as the README says. Where several hosts verify responses, the invalidation store must be shared between them.
**Recommendation:** Keep the README guidance as it is. Integrators invalidate by challenge. The response bytes are not a stable key.

### [AUTH-006] [info] The device signature covers the envelope, not the seal, so the session key belongs to whoever sealed the response
**Location:** `src/response_cipher.js:96-137`, `src/challenge_response_flow.js:228-234`, `src/api/authentication.js:248`
**Description:** The session key is an HPKE export of the sealing context, so the application shares it with the party that sealed the response. HPKE base mode does not authenticate that party. The device signature inside the envelope proves who made the envelope. The seal to `ek` proves that only the application that stores the challenge can open it. Nothing ties the seal to the signature. A party that has the plaintext envelope can seal it again to the same `ek`. The application then accepts the sign-in and derives a session key that this party knows and the user's authenticator does not. The plaintext envelope exists only in the authenticator page and in the memory of the verifying process, and the library never returns or logs it. The condition therefore requires a compromise that already defeats the sign-in. The property still matters for the guarantee the README states, that only the application and the user's authenticator know the session key. That guarantee is true under this condition and not in general. The HPKE steps follow RFC 9180 as read. The labeled extract and expand inputs, the base-mode context and the exporter derivation are in the documented order.
**Recommendation:** No change is required for the current flows. If the guarantee should stand on its own, the authenticator can mint the ephemeral key pair before it signs. It then derives the session key and puts its `skid` into `signedMetadata`. `authenticate` then compares `RequestCipher.skid(sessionKey)` with the signed value and rejects a mismatch. This is a wire change on the authenticator side and a small check here, and it is cheapest before the wire freeze.

### [AUTH-007] [info] A delegated sign-in authenticates the subject by default, and only the `actor` field tells it apart
**Location:** `src/api/authentication.js:237-242`, `src/signature.js:343-357`, `src/challenge_response_flow.js:305-312`
**Description:** When the subject's identity records publish a grant for the actor, a response signed by the actor's keys returns `{authenticated: true, identifier: <subject>}`. The grant has `auth` in its `use` and the service host in its `scope`. `verifyChallengeResponse` sets no `actor` constraint, and no configuration option refuses delegated sign-ins. The result reports the delegation in `actor`, `actorIdentityDomain` and the composite `deviceTag`, and the README's result table documents those fields. The trust model makes the zone that publishes the records the authority over who signs in as the identifier. A grant is published there in the same way as a key, so the behaviour is consistent with the protocol. An application that treats `identifier` as the signed-in person has to decide on its own whether a delegate may act in that role. A consent or a payment approval is such a case. The Best Practices section does not say so.
**Recommendation:** Add one Best Practices bullet. An application that requires the subject in person checks `actor === ''` on the result, and every other application records `actor` with the session. A `config` option that rejects delegated results with `verification_failed` would give the same outcome as a secure default. The cost is one more configuration key.

### [AUTH-009] [low] The README's Express example keeps the same session identifier across the sign-in
**Location:** `README.md:209-227` (the `/callback` handler of the Node.js example), `README.md:2035-2105` (Best Practices and Security Considerations)
**Description:** The Express example stores the challenge in the `express-session` session of the browser that started stage 1. After a successful stage 3 it writes the identifier into that same session. The session identifier in the `connect.sid` cookie does not change at any step of the sign-in. An attacker who can set a cookie for the application's host in the victim's browser plants a session identifier there. The attacker obtained that identifier from the application. A sibling subdomain, a plain-HTTP response on the path to the application, or a script injection gives that ability. The victim then signs in. The challenge is stored in the planted session. The victim approves the request at their own authenticator. The callback then marks the planted session as signed in with the victim's identifier. The attacker, who knows that session identifier, has the victim's session with its device tag and session key. This is session fixation. The sealed response and the server-side challenge bind the response to the session. Session fixation attacks the session itself, so the protocol makes no difference to this class. The library never sees the HTTP session, so the remedy is in the integration. The Best Practices section has bullets on the server-side session, on cross-site requests to the stage-1 endpoint and on rate limits. It has none on the renewal of the session identifier at sign-in.
**Recommendation:** Add one Best Practices bullet. When a stage-3 result has `authenticated: true`, renew the session identifier before the identifier, the device tag and the session key are stored. In `express-session`, `req.session.regenerate` does this. The Express example can show that call in its `/callback` handler. A session cookie with the `Secure` and `HttpOnly` attributes and a host-only scope narrows the ways to plant one. The renewal closes the attack for every way.
