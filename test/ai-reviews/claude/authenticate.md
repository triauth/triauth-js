# Fable 5.1 review — Triauth.authenticate

## Summary

`Triauth.authenticate` verifies a stage-3 response along one path. `ChallengeResponseFlow.perform` opens the sealed response with the decryption key kept with the stored challenge, and `verifyChallengeResponse` runs the envelope through `Response.verify`, `MultiSignature.verify` and `Signature.verify`. The seal is HPKE in base mode with a fresh P-256 key pair per challenge. A response therefore opens only with the challenge it was made for. Any change to it fails the AES-GCM tag before a single DNS query is made. The device signature covers the exact challenge bytes, with the encryption key inside them. It also covers the envelope type, the identifier, the actor, the `via` base URL, the device timestamp and the signed metadata. The verifier pins exactly one envelope segment and the challenge type. It checks the identifier equality before any DNS query, and the freshness windows of the challenge and of the signature. It checks the key `use` option, a complete key group, and the WebAuthn origin of the resolved endpoint. For delegation it checks the include grant with its flow and its service host. It checks the private-mode commitment and the equality of the signature's `via` with the base URL of the challenge's `cburl`. Every parse and constraint failure fails closed, and a DNS failure is reported as the retryable error `dns_unavailable` instead of a false verdict. The error objects carry string codes with a `reason` on validation errors, and the JSON parser admits only safe integers, well-formed strings and ASCII member names outside the prototype names. The compressed P-256 key form that `es256` and `webauthn-es256` records accept is decoded with a field-prime bound, a curve check and a parity rule. I found no way to authenticate as an identifier without a signature from keys that its identity records publish or delegate to.

The headline concern is AUTH-001, which the founder accepted as by design on 2026-10-01. The seal also closes the response-injection form of login CSRF on its own. A captured (challenge, response) pair of an attacker's own sign-in does not open in a victim's session, because the decryption key lives with the victim's challenge. The identifier-injection form stays open at the integrator's stage-1 endpoint, and the README does not mention it. AUTH-008 records that as a low item with a Best Practices bullet as the remedy. AUTH-006 records that the session key is derived from the seal and not from the signature, as a property to know rather than a defect. The remaining items are hardening notes on the delegated path, on logs, on the stage-1 redirect, on replay, and on delegated sign-ins.

The library is safe to use in mission-critical production systems when the deployment follows the README. The stored challenge stays server-side, out of URLs and logs, and is invalidated after every attempt. The session key is stored with the server-side session. Strict deployments set `config.requireSecure`. Both stages are rate limited, and the stage-1 endpoint accepts only requests that the application's own page made. This review is grounded on the trust model page, read from the triauth-www checkout, on the code and on the README. The 102 Authentication API unit tests and the 1581 JSON conformance cases pass on this tree.

## Findings

### [AUTH-001] [medium] [reviewed] Stage 3 binds the response to the challenge's callback URL, not to the verifying application's
**Location:** `src/challenge_response_flow.js:210-216` (optional `callbackUrl` constraint), `src/challenge_response_flow.js:285` (`via` must equal the base URL of `challenge.data.cburl`), `src/api/authentication.js:228-247` (the result carries neither `via` nor `cburl`)
**Description:** The only site binding that the verifier enforces on its own is `getBaseUrl(challenge.data.cburl) === sig.via`. Both values come from the same source. The challenge supplies `cburl`, and the authenticator derives `via` from that same `cburl` before it signs. The verifier therefore proves that the response belongs to the challenge, not that the challenge belongs to the application that verifies it. The stage-3 `callbackUrl` option closes that gap, but it is optional, and the success result exposes neither `via` nor `cburl`, so an application cannot check the site binding after the fact.

This is a secure-default gap, not a bypass. When the challenge is held server-side, as the Best Practices require, it carries the application's own `cburl` and the binding is complete. When the challenge travels through the client, as in the README's browser example or in a single-page app whose API receives both `challenge` and `response` from the browser, a genuine response can be substituted across sites. An attacker runs an ordinary triauth sign-in on a site of their own. A victim signs in there, and the attacker's server receives a genuine (challenge, response) pair for the victim, with `cburl` and `via` naming the attacker's site. The attacker submits that pair to the target application. Every check passes, and the target signs the attacker in as the victim. This is the same class as the token substitution attacks on OAuth implicit flows, which audience checks close. The GET and HASH callback methods, documented as useful for client-side applications, make the client-held pattern likely in practice.
**Recommendation:** Require the application's `callbackUrl` in stage 3 of `authenticate` (and of the other challenge-response methods), so that `challengeObj.data.cburl` is always compared with a value the server controls. This is a code-only change with no wire impact. If the option stays optional, return `callbackUrl` (or `via`) on the success result so an application can pin it, and promote the stage-3 `callbackUrl` constraint from a side note to a Best Practices rule for every deployment where the challenge is not held server-side.
> **Human review (triauthor, 2026-10-01):** By design. The challenge is server-side state. Stage 3 verifies a response against the challenge the application itself issued and stored, so the callback URL in it is already the application's own. A client-side application cannot trust any verification it performs itself, whatever the library checks. A backend that needs proof of identity runs the flow on its own, or asks for a `stamp` or `sign` over a nonce it issued and verifies the result with `via` pinned. The README states both rules. Accepted.

### [AUTH-002] [low] Delegated path resolves and verifies the actor before the subject's grants are consulted
**Location:** `src/signature.js:313-357`
**Description:** For an envelope with a non-empty `actor` slot, `Signature.verify` resolves the actor's identity (two DNS resolutions on the actor's domain) and verifies the crypto signatures against the actor's keys. Only then does it resolve the subject and search its include records. The `actor` slot is chosen by whoever submits the response, and it may name any domain. A stage-3 request must first open under the challenge's key pair, so the sender needs the readable challenge of a stage-1 call. That is no obstacle to the party that started the flow, which receives the challenge in the `redirectUrl`. The request then drives DNS lookups to an attacker-chosen domain and a full key-group verification before the subject's records, which decide the outcome, are read. This happens even when the subject publishes no include record at all, which is the common case. The outcome is still `verification_failed`. The cost is DNS egress, CPU, and a query that the attacker's name servers observe. The crypto cost is bounded, because the key-group loop stops at the first key that no signature matches, so one envelope costs at most ten devices times ten signature checks. Stage 1 already allows a lookup of an attacker-chosen domain through the identifier, so the gain for an attacker is small, and the README's rate-limit guidance bounds the volume.
**Recommendation:** Resolve the subject first. If the subject publishes no include whose `domainName` equals the actor's domain, a string comparison on parsed records with no DNS, return `false` before the actor is resolved. Keep the existing include match (actor ref, flow and service host) after the actor resolves. The order change alters no verdict, since both resolutions are required for a delegated success and either failure yields the same result.

### [AUTH-003] [info] Info and debug logs include device tags with lookup codes and the full verification result
**Location:** `src/api/authentication.js:218`, `src/challenge_response_flow.js:124`, `src/response.js:148`
**Description:** `authenticate` logs `deviceTag` at info level. Under `mode=private` that value includes the lookup code, and for a delegated sign-in also the actor's identifier. Stage 1 logs the identifier, the callback URL and the requested `ext` at info level. `Response.verify` logs the complete verification result at debug level, with the signed metadata, the lookup codes, the device tag and the public key values. Neither the session key nor the decryption key of the stored challenge is passed to the logger on any path I traced. The opened envelope is not logged either. The error path logs the thrown error as `cause` at info or warn level, and none of the errors on the stage-3 path carries a challenge, a key or an envelope in its data. The default logger runs at the error level, so nothing is emitted out of the box. The Logging section of the README states that debug output contains sensitive protocol artifacts. It states that info output contains identifiers, callback URLs, `ext` options and device tags with lookup codes, and that operators review that output before it goes to a third party. The remaining exposure is an operator who raises the level on a shared log pipeline against that advice.
**Recommendation:** Keep the README warning. If a cheaper safeguard is wanted, redact the `~<lookupCode>` suffix of `deviceTag` in the info line of `authenticate`, so that the lookup code appears only at debug level.

### [AUTH-004] [info] Stage 1 redirects to the host that the identifier's domain publishes
**Location:** `src/challenge_response_flow.js:153-172`, `src/authentication_endpoint.js:101-114`
**Description:** The `redirectUrl` is `https://<host>/auth.html#?challenge=...`, where `<host>` is the value of the `triauth` TXT record of the domain in the user-typed identifier. The host passes the domain-name grammar and nothing else. An application whose sign-in endpoint accepts the identifier from a GET parameter therefore acts as an open redirector to any https host that a zone operator chooses. This is inherent to the protocol, in the same way as identity-provider discovery in federated sign-in. The README asks for a top-level navigation so that the user sees the authenticator's origin. The redirect happens in the browser, so the server never connects to that host. Stage 1 resolves only the endpoint record, never the identity records, so it does not reveal whether the identifier exists. The challenge travels readable in the URL fragment, so the authenticator page can read the identifier and the callback URL, which the Privacy Considerations section of the README documents.
**Recommendation:** Integrators should start stage 1 from a POST form rather than from a link, and protect that form as AUTH-008 describes. They may show the authenticator host (the host part of `redirectUrl`) to the user before the redirect. No library change is required.

### [AUTH-005] [info] Verification is stateless, so replay protection is the application's duty
**Location:** `src/challenge_response_flow.js:300-307`, `src/response.js:113-127`, `src/config.js:71`
**Description:** A valid (challenge, response) pair verifies again on every call while the challenge `iat` is inside the `authTimeout` window and the signature `ts` is inside the client clock drift. The window is three minutes by default, widened by the server clock drift. The challenge nonce makes each challenge unique, but the library keeps no state and cannot reject a second presentation. Each presentation also yields the same session key, so a replayed response gives the application a second session with the key of the first. The README prescribes invalidation of the stored challenge after every attempt and a monotonic `issuedAt` check. AES-GCM detects any change to the sealed string, and an outsider cannot open or re-seal it. A second response string with different bytes can therefore come only from a party that has the plaintext envelope. Deduplication therefore keys on the challenge, as the README says. Where several hosts verify responses, the invalidation store must be shared between them.
**Recommendation:** Keep the README guidance as it is. Integrators invalidate by challenge, not by response.

### [AUTH-006] [info] The device signature covers the envelope, not the seal, so the session key belongs to whoever sealed the response
**Location:** `src/response_cipher.js:96-137`, `src/challenge_response_flow.js:225-229`, `src/api/authentication.js:248`
**Description:** The session key is an HPKE export of the sealing context, so the application shares it with the party that sealed the response. HPKE base mode does not authenticate that party. The device signature inside the envelope proves who made the envelope. The seal to `ek` proves that only the application that stores the challenge can open it. Nothing ties the seal to the signature. A party that has the plaintext envelope can seal it again to the same `ek`. The application then accepts the sign-in and derives a session key that this party knows and the user's authenticator does not. The plaintext envelope exists only in the authenticator page and in the memory of the verifying process, and the library never returns or logs it. The condition therefore requires a compromise that already defeats the sign-in. The property still matters for the guarantee the README states, that only the application and the user's authenticator know the session key. That guarantee is true under this condition and not in general. The HPKE steps follow RFC 9180 as read, with the labeled extract and expand inputs, the base-mode context, and the exporter derivation in the documented order.
**Recommendation:** No change is required for the current flows. If the guarantee should stand on its own, the authenticator can mint the ephemeral key pair before it signs, derive the session key, and put its `skid` into `signedMetadata`. `authenticate` then compares `RequestCipher.skid(sessionKey)` with the signed value and rejects a mismatch. This is a wire change on the authenticator side and a small check here, and it is cheapest before the wire freeze.

### [AUTH-007] [info] A delegated sign-in authenticates the subject by default, and only the `actor` field tells it apart
**Location:** `src/api/authentication.js:237-242`, `src/signature.js:343-357`, `src/challenge_response_flow.js:300-307`
**Description:** When the subject's identity records publish an `include` grant for the actor, a response signed by the actor's keys returns `{authenticated: true, identifier: <subject>}`. The grant has `auth` in its `use` and the service host in its `scope`. `verifyChallengeResponse` sets no `actor` constraint, and no configuration option refuses delegated sign-ins. The result reports the delegation in `actor`, `actorIdentityDomain` and the composite `deviceTag`, and the README's result table documents those fields. The trust model makes the zone that publishes the records the authority over who signs in as the identifier. A grant is published there in the same way as a key, so the behaviour is consistent with the protocol. An application that treats `identifier` as the signed-in person has to decide on its own whether a delegate may act in that role. A consent or a payment approval is such a case. The Best Practices section does not say so.
**Recommendation:** Add one Best Practices bullet. An application that requires the subject in person checks `actor === ''` on the result, and every other application records `actor` with the session. A `config` option that rejects delegated results with `verification_failed` would give the same outcome as a secure default. The cost is one more configuration key.

### [AUTH-008] [low] The stage-1 endpoint accepts a cross-site request, so a victim's browser can be signed in as the attacker
**Location:** `README.md` (Best Practices and Security Considerations, and the Node.js example at `README.md:182-202`), `src/challenge_response_flow.js:103-179` (stage 1 binds the challenge to no browser)
**Description:** Stage 1 takes an identifier and returns a challenge. Nothing in the challenge ties it to the browser that asked for it. An attacker publishes a `triauth` record and identity records for an identifier in a zone they own, with their own authenticator at the published host. They make the victim's browser submit the application's stage-1 form with that identifier, through an auto-submitting cross-site form, or through a top-level navigation when stage 1 accepts a GET. The application stores the challenge in the session that the request carries and redirects the victim to the attacker's authenticator. That authenticator holds the attacker's keys, approves without a prompt, seals a genuine response to the challenge's `ek`, and redirects the victim back to the callback URL. Every stage-3 check passes, because the response is genuine for that challenge. The victim's browser now holds a session signed in as the attacker's identifier, and the victim may enter data into the attacker's account. This is login CSRF, the class that a CSRF token on the sign-in form closes in federated sign-in. A `SameSite=Lax` session cookie does not close it. A cross-site POST arrives without the cookie, the application opens a new session for it, and the response sets that session's cookie in the victim's browser in place of the old one. The sealed response closes the other form of this attack. A captured (challenge, response) pair of the attacker's own sign-in does not open in the victim's session, because the decryption key lives with the victim's challenge. The same cross-site request to the stage-3 callback can end a pending sign-in early, with `false` or any other string as the response, which costs the victim one retry. The README's Express example stores the challenge in `express-session` behind a plain POST form with no CSRF token, and the Best Practices section does not mention cross-site requests.
**Recommendation:** Add one Best Practices bullet. The stage-1 endpoint accepts only requests that the application's own page made, through a CSRF token or a check of the `Origin` header, and never through a GET. The Express example can carry that token. No library change closes this, because the library does not see the HTTP request.
