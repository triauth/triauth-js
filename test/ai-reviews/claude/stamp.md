# Fable 5.1 review — Triauth.stamp

## Summary

`Triauth.stamp` verifies one fresh signature over the challenge message and nothing else. The stage-3 path is strict and fails closed. The stored challenge carries the private key that opens the sealed response, the sealed response is opened and authenticated with AES-GCM before any field of the envelope is parsed, and the HPKE construction is pinned by the RFC 9180 known-answer vector. The envelope grammar is closed, metadata goes through a bounded JSON parser that admits only safe integers and ASCII member names, and the three-state verdict keeps `verification_failed` and `request_expired` apart. The flow type, the identifier, the message and the callback base URL are all pinned to the stored challenge. Key use gating excludes keys that are not published for `stamp`, and `requireSecure` turns the DNSSEC flag into a hard gate at both stages. The es256 verifiers accept a compressed P-256 point through a decoder that rejects an x at or above the field prime and an x off the curve, so each key has one compressed spelling and the accept set is the same on every runtime. The error catalog is string codes with a `reason` on validation errors, and the `stamp.json` vectors pin every security property that the code claims, including the replay window and the sealed-response rejections. All 1581 conformance cases pass at this commit.

The headline concern remains the replay surface of the design. A stamp covers neither the challenge nonce nor the challenge encryption key, so the plaintext `result` re-verifies against any later stamp challenge for the same identifier, message and base URL for about 45 seconds. Sealing narrows who can exercise it. A wire observer sees only ciphertext, and a replay needs the plaintext stamp plus the encryption key of a fresh challenge, which only the application and the holder of the session key can read. The README documents the property and requires a verifier-chosen nonce inside the message (STAMP-001, accepted by design). Two low findings are open. Stage 3 accepts the `sessionKey`, `ext`, `message` and `attachments` options and ignores every one of them, so none of them binds or cross-checks anything, which a probe against the suite fixtures confirms (STAMP-007). The `actor` slot of a response directs DNS resolution and key verification at an arbitrary domain before the subject's grant is checked, although only a holder of the challenge encryption key reaches that path (STAMP-002). The one recommendation of this review is to reject at stage 3 every option that stage 3 does not check, as stage 1 rejects `attachments`. Five informational notes cover device continuity, documentation drift, unauthenticated metadata, log contents, and the lookup code that a private-mode stamp carries inside the `result` that the README invites integrators to forward.

The library is safe to use in mission-critical production systems. No finding reaches high. Such deployments must put a single-use nonce into every stamped message, pin `via` in third-party verification, keep the stored challenge and the session key in server-side session state, and set `requireSecure` where their identities support DNSSEC.

## Findings

### [STAMP-001] [medium] [reviewed] The challenge nonce is not bound to the stamp, so a stamp over a fixed message is replayable for about 45 seconds
**Location:** `src/api/signing.js:102-104`, `src/challenge_response_flow.js:270-287`, `src/response.js:113-141`
**Description:** The signed bytes of a stamp are `stamp;identifier;actor;via;v1;ts;signedMetadata;;msg`. The challenge nonce, `iat` and `cburl` stay outside them, and stage 3 never compares anything in the response with the nonce. Freshness rests on two windows that are measured against the verifier clock and are independent of each other. The challenge `iat` must fall within `stampTimeout` plus 5 s of server drift. The envelope `ts` must lie between 45 s before and 30 s after the verifier clock, which is `stampTimeout` plus the client drift behind and the client drift ahead. A captured stamp therefore verifies against any later stamp challenge for the same identifier, message and callback base URL for up to 45 s after it was minted. The `stamp.json` vectors pin this with the different-nonce, sibling-callback and 45 s replay cases. Stage 1 does not tie the token to the identifier on the server, so an application that takes the identifier from the request lets a caller mint a challenge for the victim's identifier in the caller's own session and redeem a leaked stamp there. The Best Practices heuristic that rejects an `issuedAt` at or below the last `verifiedAt` does not cover this case, because a fresh challenge carries a fresh `issuedAt`. The README documents the property and requires a verifier-chosen nonce inside `message`, and the example follows the rule. The risk remains for integrators who stamp a fixed message, for instance as a session proof or an API credential, and whose responses leave TLS, for example through `callbackMethod` GET, where the stamp lands in URLs, logs and analytics. The impact is identity spoofing at that application. The likelihood is low, which gives medium.
**Recommendation:** Make stamps single-use by default while the wire format is still open. Have the authenticator copy the challenge nonce into the signed metadata, for example as `nonce`, and have stage 3 of `stamp` (and `sign`) require `sig.signedMetadata.nonce === challenge.data.nonce`. `Triauth.verify` ignores the member, so stamps stay portable. A smaller step that needs no authenticator change is to reject a stamp whose `ts` precedes the challenge `iat` by more than `maximalAllowedClientClockDrift`, which trims the window to about 30 s.
> **Human review (triauthor, 2026-10-01):** By design. Stamps are portable proofs, so the challenge nonce stays outside the signed bytes on purpose. Replay protection is a fresh, single-use nonce that the verifier places inside the message, which the README requires and the stamp.json vectors pin together with the 45 s window. Accepted.

### [STAMP-002] [low] The `actor` slot of a response directs DNS resolution and key verification at an arbitrary domain before the subject's grant is checked
**Location:** `src/signature.js:313-357`, `src/response.js:134-141`, `src/identity_includes.js:217-233`, `src/challenge_response_flow.js:315`
**Description:** For a delegated envelope, `Signature.verify` resolves the actor identity first. That reads the endpoint record and the identity records of the actor's domain, at a label derived from the `actorLookupCode` in the signed metadata, and then verifies the crypto signatures against the keys that domain publishes. Only after a key group matches does it resolve the subject and look for a matching include grant. In the stamp flow the subject is pinned to the challenge identifier, but the actor slot is free text under the sender's control, and `Response.verify` passes neither `actor` nor `via` as a constraint. A response reaches this path only when it is sealed to the challenge's `ek`, so the sender must hold that key. The application holds it, and so does the user whose session key opens the sealed request in the redirect URL, because the authenticator runs in that user's browser. A signed-in user with a pending stamp challenge can therefore post an envelope that names `anyone@attacker-chosen.example` as the actor. Every such request makes the verifier query that domain through all configured resolvers and verify up to `maxDevices` times `maxKeysPerSignature` signatures against attacker-published keys, and ends in `verification_failed`. Each attempt costs the sender a stage-1 call when the application forgets the challenge after stage 3 as the README requires, the work per request is bounded, and the README asks for rate limiting of both stages, so the exposure is cost amplification and an attacker-triggered outbound DNS query, not a bypass. The same ordering lets a stamp whose `via` differs from the challenge callback base reach DNS and crypto before the comparison at `challenge_response_flow.js:315`.
**Recommendation:** Resolve the subject first. Filter its include statements by the actor's domain (every include ref carries it), by the flow in `use`, and by the `via` host in `scope`, and reject without any actor-side DNS when no candidate remains. Pass the expected `via`, the base URL of the challenge `cburl`, into the `Response.verify` constraints so that a mismatch is rejected before resolution.

### [STAMP-003] [info] Stage 3 does not tie the stamp to the device or actor that holds the session key
**Location:** `src/challenge_response_flow.js:300-330`, `src/api/signing.js:88-161`, `README.md:1471-1480`, `README.md:2060-2062`, `README.md:2067`
**Description:** A stamp is accepted from any valid device key of the identifier, and from any delegate whose include grant covers `use=stamp` and the callback host. The authenticator binds the session key of a sign-in to the device that signed in, but stage 3 cannot see which device answered. The session key exported from the sealed stamp response is a fresh value of that response, not the key of the sign-in, and stage 3 discards it. Stage 3 takes no `deviceTag` or `actor` option, so continuity with the session that obtained the key is left to the integrator. The result exposes `deviceTag` and `actor` inside `verificationResult`. The Best Practices section asks to store the `deviceTag` and the `sessionKey` in the session and to re-check with `check` or `ping`, and the result table says to read the signer's `deviceTag` from `verificationResult`, but neither the README stamp section nor the JSDoc says to compare it with the session's `deviceTag` at stage 3. An integrator who reads a stamp as proof that the device of this session is still present may accept a stamp from another device of the same user or from a delegate.
**Recommendation:** Accept optional `deviceTag` and `actor` options at stage 3, checked against the verified signature like the optional `identifier` and `callbackUrl`. Say in the stamp section that an integrator compares `verificationResult.deviceTag` with the session's `deviceTag`, and requires `actor === ''` where delegation is not wanted.

### [STAMP-004] [info] The README stamp section omits the replay warning that the JSDoc carries
**Location:** `README.md:1312-1314`, `src/api/signing.js:383-388`
**Description:** The JSDoc of `stamp` has a WARNING block that says stamps are not single-use proofs and that a stamp over a fixed message re-verifies against any challenge that reuses that message within the freshness window. The README stamp section has no such block. The replay rule appears only in the Best Practices section at the end of the README, in the Synopsis warning about browser-side use, and in a code comment inside the example. The section also says that a stamp proves that the user "is currently logged in", which reads as a session property, while a stamp proves key possession within a time window.
**Recommendation:** Copy the JSDoc WARNING into the README stamp section and reword the "currently logged in" sentence.

### [STAMP-005] [info] `unsignedMetadata` on a stamped result is not integrity-protected by the signature
**Location:** `src/api/signing.js:152-158`, `src/signature.js:405-406`, `README.md:1600`
**Description:** The unsigned slot of the envelope is outside the signed payload by design, because WebAuthn assertion data travels there. Stage 3 parses it with the bounded JSON parser and copies it verbatim into `verificationResult.unsignedMetadata`. The stamp vectors pin that a response whose unsigned slot was swapped after signing still returns `stamped:true`. On the stage-3 path the sealed response is authenticated under the challenge key, so a party between the authenticator and the application cannot change the slot in transit. The holder of the challenge encryption key can, and so can anyone who handles the plaintext `result` before a third party verifies it. The README verify table says that the slot is outside the signed part of the envelope, but not that its content must not drive decisions. An integrator who stores or acts on its content treats unauthenticated data as part of a verified result.
**Recommendation:** State in the `Triauth.verify` result table and in the stamp section that `unsignedMetadata` is unauthenticated input that must not drive decisions, or drop the field from the stamped result shape. The raw `result` string still carries it for third-party verification.

### [STAMP-006] [info] Info-level logs include the `deviceTag` with its private-mode lookup code
**Location:** `src/api/signing.js:146`, `src/response.js:148`, `README.md:1911-1913`
**Description:** On success, stage 3 logs the identifier and the `deviceTag` at info level, and `Response.verify` logs the whole verification result at debug level. Under `mode=private` the `deviceTag` carries the lookup code as a `~` suffix, and the README lists `deviceTag` and `lookupCode` among the values not to disclose to third parties. The Logging section warns that the info level logs device tags that can contain a lookup code and asks to review that output before forwarding it. The default log level is error, so nothing is emitted unless the integrator raises it, but a raised level with a hosted log service forwards these values.
**Recommendation:** Log the `deviceTag` without its `~lookupCode` suffix at info level, and keep the full tag at debug level.

### [STAMP-007] [low] Stage 3 accepts the `sessionKey`, `ext`, `message` and `attachments` options and ignores them
**Location:** `src/challenge_response_flow.js:78-85`, `src/challenge_response_flow.js:100`, `src/challenge_response_flow.js:223-229`, `src/api/signing.js:50-57`, `src/api/signing.js:75-100`
**Description:** The option whitelist of every flow that follows a sign-in admits `sessionKey` and `ext` in both stages, and the stage-3 branch declares its own `sessionKey` from the opened response, so the option values are never read there. `_perform` removes `message` and `attachments` from the options before the whitelist runs and reads them only inside `onChallenge`, which runs at stage 1. At stage 3 the message comes from the stored challenge, and the attachments rule of stamp looks at the challenge and at the signed metadata, never at the option. A probe against the `stamp.json` fixtures at this commit confirms it. `Triauth.stamp({challenge, response, sessionKey: 'not-a-session-key'})`, the same call with `ext: {callbackMethod: 'POST'}`, with `message: 'A completely different message'`, with `message: 12345`, with `attachments: [...]` and with `attachments: null` all return `stamped:true`, while an unknown key returns `invalid_arguments` and a mismatching `identifier` returns `verification_failed`. The optional `identifier` and `callbackUrl` options at stage 3 are checked against the challenge, so an integrator may expect the same of `sessionKey` and `message`, and believe that the stamp is bound to the session that holds the key, or that a message kept outside the challenge is cross-checked. No session binding exists (see STAMP-003), and the library cannot provide it today, because the session key exported from a stamp response is a fresh value of that response. The message in the stored challenge is authoritative, so the ignored `message` option weakens nothing on its own, but a stage-3 `message` that differs from the challenge is a sign of a mixed-up session that passes silently. Stage 1 rejects `attachments` with `invalid_arguments`, which is the pattern stage 3 lacks. The `stamp.json` vectors carry no stage-3 case with a `sessionKey`, `ext`, `message` or `attachments` option, so the acceptance is unpinned.
**Recommendation:** Reject `sessionKey`, `ext` and `attachments` at stage 3 with `invalid_arguments`, as stage 1 rejects `attachments`, and either reject `message` the same way or check it against `challenge.data.msg` like `identifier` and `callbackUrl`. State in the JSDoc and the README which options belong to which stage, and pin the chosen behaviour in `stamp.json`. If a later wire revision lets the authenticator sign the session key ID into the response, a stage-3 `sessionKey` option can then be checked instead of refused.

### [STAMP-008] [info] A private-mode stamp carries the lookup code inside the `result` that the README invites integrators to forward
**Location:** `src/signature.js:309-313`, `README.md:1476`, `README.md:2060-2062`
**Description:** Under `mode=private` the authenticator places `lookupCode` in the signed metadata, because a verifier needs it to derive the label of the identity records. `Signature.verify` reads it from there, so a private-mode stamp verifies only when the code travels with it. The `result` of a stamped response is the envelope verbatim, which carries the identifier in clear text and the lookup code in plain base64url. The stamp result table says to store `result` or forward it to a third party, while the Best Practices section asks to treat `lookupCode` like the identifier and not to disclose it except to its owner. Any party that receives `result` can therefore read the identity records of the signer, which list the devices, the public profile and the groups, for as long as the code stays valid. A third party that verifies the stamp needs both values, so the disclosure is a property of the portable proof and not a defect, but the documentation does not let an integrator see that forwarding `result` discloses more than the identifier.
**Recommendation:** Say in the stamp and sign result tables that under `mode=private` the `result` carries the lookup code next to the identifier, so it is forwarded only to parties that may read the identity records. The same note covers `verificationResult.lookupCode` and the `~` suffix of `verificationResult.deviceTag`.
