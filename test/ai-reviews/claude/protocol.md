# Fable 5.1 review — Triauth.protocol

## Summary

The protocol core is sound. The signature envelope has a closed grammar. No slot before the message admits the `;` delimiter. One envelope string therefore parses to exactly one set of fields. One signed payload maps to one tuple of type, identifier, actor, via, version, timestamp, signed metadata, and message. The unsigned metadata slot is the only unsigned field. The WebAuthn verifier binds its contents through the assertion signature and the challenge digest. Key material comes only from DNS, read through an intersection of independent resolvers. The verifier fails closed on every malformed record, tainted key group, unknown critical key option, missing commit record, missing include grant, and unavailable crypto verifier. A P-256 key is accepted in its uncompressed or its compressed form. The decoder checks the field bound and the curve equation itself, so the accepted set is the same on every runtime. This was confirmed against Web Crypto during this review. WebAuthn assertions must match the resolved authenticator origin and must have the user-presence flag. A delegated signature needs a grant in the subject's own records that covers the actor, the flow, and the service host. Its device tag changes with the grant, the actor's identity domain, and the actor's keys.

The transport around the envelope is sealed. Every challenge includes a fresh P-256 public key. The authenticator seals its response to it with HPKE in the DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-128-GCM suite. The implementation follows RFC 9180 step by step and reproduces the test vector of its appendix A.3.1 in the test suite. It checks the peer point for length and prefix before the curve import. It binds the key schedule to the protocol and version through the `info` label. A response sealed to one challenge does not open under another, so a foreign response delivered to a callback fails before any signature is read. Base mode authenticates no sender. The signatures inside the envelope remain the only proof of origin, which the code states. Both sides export the session key from the same encryption context, so it never travels. The requests after a sign-in travel under AES-128-GCM with a key that HKDF derives from the session key. Each request gets a fresh random IV from Web Crypto.

The documented limits held up under review. The challenge is not server-signed, and replay protection for `auth` and `ping` rests on the integrator invalidating the stored challenge. `sign` and `stamp` results are transferable within their freshness window, and the `via` check stops their use at another site. DNS integrity for an unsigned zone rests on resolver cross-validation unless `requireSecure` is set. The README states each of these.

No finding is above low. The library is safe for mission-critical production use when it is deployed as the Best Practices section describes. The challenge stays in a server-side store and is invalidated after each attempt. The session key is stored with the server-side session. The stage-1 and stage-3 endpoints are rate-limited, and the request that starts stage 1 is accepted only from the application's own pages. `config.requireSecure` is set to `true` so that an answer without DNSSEC is rejected instead of reported.

The one change to make before launch is PROTO-009. An attestation is accepted from any identity at the provider's host. The default therefore cannot tell a provider apart from the other identities of a shared host. Let the integrator pin the attester identifier per provider.

## Findings

### [PROTO-001] [low] Duplicate-segment guard compares bytes, so one key can fill several segments
**Location:** `src/multi_signature.js:77`, `src/verifiers/ecdsa.js:89`
**Description:** `MultiSignature` rejects an envelope only when two of its segments are byte-identical. The signed content of a segment excludes the unsigned metadata slot and the encoding of the crypto signature. A second segment with the same signed content therefore passes the guard in two ways. The sender can fill the unsigned slot with a value that decodes to `{}`, which the ECDSA and Ed25519 verifiers ignore. Or the sender can replace an ECDSA signature `(r, s)` with `(r, n - s)`, which Web Crypto accepts. This was confirmed again with the runtime's Web Crypto during this review. The README already says that `minSignatures` counts segments and not signers. The attestation flow matches one segment per requested attestation. The practical effect is a guard that is weaker than its comment states. An integrator who keys a replay store on the raw envelope string gets the same two bypasses.
**Recommendation:** Deduplicate on the signed fields of each segment, which are the first seven slots of the envelope, and reject an envelope that repeats them. Optionally reject an ECDSA signature whose `s` value is above half the curve order. State in the README that an envelope string is not a unique identifier of a signature.

### [PROTO-002] [low] Transferable proofs of a private-mode identity disclose its lookup code
**Location:** `src/signature.js:309-310`, README "Best Practices and Security Considerations"
**Description:** Under `mode=private` the verifier derives the identity domain from the lookup code that the envelope states in `signedMetadata.lookupCode`, and from `actorLookupCode` for a delegated signature. `Triauth.verify` has no other way to receive it. A `sign` or `stamp` result is therefore a container for the lookup code. Forwarding the `result` string to a third party for verification gives that party the code. The sealed transport does not change this, because the `result` string is the opened envelope. The README asks integrators not to disclose `lookupCode` and `actorLookupCode` to third parties. It does not say that the `result` string of `sign` and `stamp` includes them.
**Recommendation:** Add one sentence to the Best Practices section and to the `sign` and `stamp` sections. A signature made for a private-mode identity includes the lookup code. Share the `result` string only with parties who may look up the identity's records.

### [PROTO-003] [info] A GET callback writes the sealed response to logs and history
**Location:** README "Protocol extensions", `src/challenge_response_flow.js:140-142`, `src/response_cipher.js:96-137`
**Description:** With the default `{callbackMethod:'GET'}` the authenticator delivers the response as a URL query parameter, which web servers, proxies, and browsers record. The response is HPKE ciphertext sealed to the `ek` of its challenge. The decryption key stays in the stored challenge, so a logged response reveals nothing on its own. The `ext.permissions` decisions and the material of the session key are inside the ciphertext. The plaintext is recoverable only by a party that has both the log line and the stored challenge. The README tells integrators to keep the challenge out of URLs and logs. The Protocol extensions table states that the encrypted response appears in the URL and in access logs. What a GET callback still discloses is the fact and the time of the callback and its callback URL. For a sign-in, the readable challenge in the redirect URL includes the identifier, as the Privacy Considerations section states.
**Recommendation:** No change to the code. Keep the sentence about logs in the Protocol extensions table. Keep the sentence in the 3-step flow note that tells integrators to keep the stored challenge out of URLs and logs. Keep recommending `POST` or `HASH` where the callback metadata itself must stay out of server logs.

### [PROTO-004] [low] One resolver on the path can deny service for a whole domain
**Location:** `src/resolvers/multi_resolver.js:128-150`, `src/index.js:89-96`
**Description:** The default `MultiResolver` returns the intersection of the answers of every resolver that responded. A single resolver cannot add a record, which is the aim of the design. A single resolver can remove every record by answering with an empty or a different set. In Node the third resolver is the system resolver over plain UDP. A party that can alter its answers for the identity domain needs no valid record data. For as long as it lasts, the altered answer makes `check` return `{valid:false, reason:'unresolved'}` and stage 3 return error 401 for every user of that domain. This is the intended trade of availability for integrity, and it fails closed. The README's resolver guidance covers relays that cut a large answer short and resolvers without DNSSEC support. It does not cover an answer that disagrees on purpose.
**Recommendation:** Document that a single disagreeing resolver vetoes an answer. Recommend a local validating resolver such as Unbound, or a DoH-only `MultiResolver`, where the system resolver path crosses an untrusted network. A partial hardening is to count an empty answer as a failure under `maxFailures` when the other resolvers agree on a non-empty answer. This removes the cheapest spoof, and an injected record still needs every answering resolver.

### [PROTO-005] [info] Grant scope matches the host of `via`, not its origin or base URL
**Location:** `src/signature.js:351`, `src/identity_includes.js:182-188`
**Description:** A delegated signature is accepted when an include grant of the subject covers the actor, the flow, and the host of the signature's `via`. The match uses the host alone. A grant with `scope=example.com` therefore covers `https://example.com/`, `http://example.com/`, and `https://example.com:8443/`, which are different origins. The authenticator identifies a site by the base URL of its callback, so one host can also serve several sites under different paths. A grant for the host covers all of them. On a host that serves several tenants on different ports, over both schemes, or under different paths, the grant is wider than the subject expects. The whois section of the README describes `scope` as the service hosts the grant works at. The `include` guidance does not state the consequence for shared hosts.
**Recommendation:** State the host-level match where the README describes the `scope` option, with a note for shared hosts. A later revision of the grant grammar can accept origin-form or base-URL entries for subjects who need a narrower grant.

### [PROTO-006] [info] Payload reconstruction re-serializes the timestamp slot instead of reusing the wire bytes
**Location:** `src/signature.js:152-163`, `src/signature.js:294-306`
**Description:** The parser accepts a `ts` slot of up to 16 digits and converts it with `parseInt`. The verifier then rebuilds the signed payload from the converted number. Above 2^53 the conversion is lossy. A wire slot of `9999999999999999` is verified against a 17-digit payload slot of `10000000000000000`. The wire grammar itself refuses that value, as confirmed again during this review. Every freshness window rejects such a timestamp, so there is no practical effect today. The same number is what `signedAt` reports.
**Recommendation:** Keep the wire string of the `ts` slot and use it in the reconstructed payload. Alternatively, bound the slot to 15 digits so that the number round-trips exactly.

### [PROTO-007] [info] Cheap rejections run after DNS resolution and signature verification
**Location:** `src/signature.js:155-156`, `src/identity_keys.js:237-241`, `src/challenge_response_flow.js:300-316`, `src/api/attestation.js:297-313`
**Description:** The `Signature` constructor accepts any number of crypto signature slots that fit in the 16 KB envelope. The `maxKeysPerSignature` cap is applied in `IdentityKeys.verify`, after the signer's identity has been resolved through DNS. In the single-signature flows `verifyChallengeResponse` compares the signature's `via` with the base URL of the challenge's `cburl`. This happens after DNS resolution and the cryptographic check. In the attest flow `Response.verify` gets no `identifier` constraint. Every segment, up to five, is therefore resolved and verified before the first segment's identifier is compared with the challenge. A response made for another site or another user costs the verifier one or more full resolutions before it is rejected. The README's rate-limiting advice bounds the effect.
**Recommendation:** Reject more than `maxKeysPerSignature` slots in the `Signature` constructor with error 225. Accept a `via` constraint in `Response.verify` and pass it through to the segment verification. Set it to the base URL of `cburl` in `verifyChallengeResponse`, so that the mismatch is caught before resolution. In the attest flow, compare the first segment's parsed identifier with the challenge before the segments are verified.

### [PROTO-008] [info] The challenge-response flows cannot require a first-party signature
**Location:** `src/challenge_response_flow.js:300-317`, `src/signature.js:343-357`
**Description:** Every flow accepts a delegated signature when the subject's records publish a matching grant. The flows expose no option to refuse delegation, and only `Triauth.verify` accepts an `actor` constraint. The result reports the delegate in `actor`. An application for which the subject's own approval matters, such as a `sign` of contractual terms, has to check `actor === ''` itself. The grant is the subject's own statement, so accepting it by default is consistent with the trust model.
**Recommendation:** Add a Best Practices note that says to check `actor` when first-party approval is required. A later revision can accept an `actor` constraint on the challenge-response flows.

### [PROTO-009] [low] An attestation is accepted from any identity at the provider's host
**Location:** `src/api/attestation.js:348-354`, README "Triauth.attest"
**Description:** The attest flow matches an attester segment to a requested attestation by three tests. The segment's `via` must be one of the listed provider URLs. The segment must be first-party. The domain of the attester's identifier must equal the host of that URL. The user part of the identifier is not checked, and neither is the path of the provider URL. Every identity in the host's zone therefore satisfies the attestation, with any device whose keys allow `attest`. Keys allow `attest` by default, and the user's own segment of an attest response needs it. On a host that is dedicated to attesters this is the intended trust anchor. On a host that also issues identities to its users, each of those users can produce an attester segment with their own keys. The README states that the method verifies only that the signature came from an identity at the provider's host. It asks integrators to compare the attester's identifier when the host also issues identities to others. The default accepts the wider set.
**Recommendation:** Let a provider entry pin its attester. Accept `{url, identifier}` beside the plain URL form in `attestations.<id>.providers`, and when the identifier is given require the attester segment to match it. Alternatively, require the user part of the attester identifier to equal the first path segment of the provider URL, as the README example already does. Until then, make the comparison of `attestations.<id>.identifier` a Best Practices item.

### [PROTO-010] [info] A stage 1 started from another site is not addressed in the README
**Location:** `src/challenge_response_flow.js:102-179`, README "Best Practices and Security Considerations"
**Description:** The stored challenge binds a response to the session that started the flow. The identifier inside it is the account that the response signs in. The library does not see the HTTP request that starts stage 1, so it cannot tell whether the user asked for that sign-in. If a sign-in form accepts a request made from another site, a third party can start stage 1 in the user's session. It can do so with an identifier of its own and complete the flow through that identifier's authenticator. The session is then signed in to an identifier the user did not choose. Redirect-based sign-in protocols in general have this property. The usual protection is to accept the stage-1 request only from the application's own origin, with a CSRF token, the `Sec-Fetch-Site` header, or `SameSite` cookies. The README tells integrators to keep the challenge in the server-side session and to prefer a fixed callback URL. It does not say to protect the request that starts stage 1.
**Recommendation:** Add one Best Practices bullet that says to accept a stage-1 request only from the application's own pages. Also show the signed-in identifier after sign-in, so that the user sees which account the session belongs to.
