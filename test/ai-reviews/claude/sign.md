# Fable 5.1 review — Triauth.sign

## Summary

`Triauth.sign` verifies one device signature over the requested `message` and the signed attachment list. It ties the result to the challenge identifier, the callback base URL, the key `use` option, and two freshness windows. The request travels sealed under the session key, and the response travels sealed to a key that only the stored challenge opens, so a response opens only for the challenge it answers. Envelope parsing is strict, metadata decoding is bounded and canonical, the crypto verifiers fail closed, and the DNSSEC status reaches both the result and the `requireSecure` gate. This review found no defect in the verification logic. The open items are low and informational. The signed bytes carry no challenge binding, so a party that knows a challenge's `ek` can re-seal an older envelope over the same message (SIGN-001). Stage 3 cross-checks `identifier` and `callbackUrl` when they are passed, and it ignores `message` and `attachments`. The result does not state the signed message (SIGN-005). Delegated signatures and the unsigned metadata slot reach the result without a note in the `sign` documentation (SIGN-002, SIGN-003). The library is safe to use in mission-critical production systems when integrators follow the documented practices, in particular a single-use nonce inside `message` wherever a signature authorizes an action, and the invalidation of each challenge after stage 3. The one recommendation of this review is to make stage 3 cross-check `message` and `attachments` when the caller passes them, and to return the signed `message` in the result (SIGN-005).

## Findings

### [SIGN-001] [low] The signed bytes carry no challenge binding, so a holder of a challenge's `ek` can re-seal an older envelope over the same message
**Location:** `src/api/signing.js:104`, `src/challenge_response_flow.js:217-229` and `:300-316`, `src/response.js:134-141`, `src/signature.js:294-306`
**Description:** Stage 3 opens the response with the decryption key that the stored challenge carries, so a sealed response opens only for the challenge it was sealed to. A sealed response captured from a URL, a log, or the browser history and presented with any other challenge fails with error 224. The signed payload holds the type, the identifier, the actor, the `via`, the version, the timestamp, the signed metadata, and the `message`. The challenge `nonce` and `ek` are outside it, and stage 3 never compares the nonce. The sealing is HPKE base mode, which does not authenticate the sender, so any party that knows a challenge's `ek` can seal any envelope to it. For a `sign` request the `ek` travels inside the request sealed under the session key. The application, the authenticator that holds the session, and any other holder of the session key know it. Such a holder can take the opened `result` of an earlier signing over the same identifier, `message`, attachments, and callback base, seal it to a fresh challenge, and obtain `signed:true` while the envelope `ts` stays inside `config.signTimeout` widened by `config.maximalAllowedClientClockDrift` on both sides (30 minutes and 30 seconds by default). The envelope `ts` may be earlier than the challenge `iat`, and stage 3 does not compare the two. Replay cannot change what was signed, and a holder of the session key can already request stamps and pings in the user's name, so the impact is limited to integrators that treat `signed:true` as a fresh approval of a message they reuse. The Best Practices bullet (`README.md:2031-2034`) and the warning in the `sign` documentation (`src/api/signing.js:172-181`) state that a captured response can be replayed against any challenge that reuses the `message`. The replay needs the opened envelope and the `ek` of the target challenge.
**Recommendation:** Compare `sig.signedAt` with `challenge.data.iat` at stage 3 and refuse an envelope whose timestamp is earlier than `iat` minus `config.maximalAllowedClientClockDrift`. This refuses an envelope produced before the challenge it answers, costs nothing on the wire, and narrows the accepted device clock skew in the `sign` flow to the configured client drift, which is the documented meaning of that setting. Bind each response to its challenge inside the signed payload once authenticators send it, for example the challenge `nonce` in `signedMetadata`, and require the binding at stage 3. `Triauth.verify` evaluates the same envelope with the same `message`, so the proof stays portable. Reword the Best Practices bullet and the `sign` warning to the sealed delivery. A captured response opens only with the stored challenge, and the opened `result` verifies against any challenge for the same `message` in the hands of a party that knows that challenge's `ek`. Keep the guidance about a single-use nonce inside `message` for every signature that authorizes an action.

### [SIGN-002] [low] Delegated signatures produce `signed:true` with no stage-3 control and no note in the sign documentation
**Location:** `src/signature.js:343-376`, `src/api/signing.js:148-160`, `README.md:1286-1300`
**Description:** When the envelope has an `actor`, `Signature.verify` accepts the signature if the actor's keys verify and the subject publishes an `include` record for the actor whose `use` covers `sign` and whose `scope` covers the callback host. An `include` record without a `use` option covers every flow (`src/identity_includes.js:98`). The result reports the subject as `identifier` and the delegate in `verificationResult.actor`. `Triauth.sign` offers no option to require the identifier's own keys, and the `sign` section of the README lists `identifier`, `deviceTag`, `secure`, and `expires` as the fields to read from `verificationResult`, without `actor`. After a delegated sign-in the session key starts with the actor's domain and the request goes to that domain's authenticator, so the application has a signal that a delegate acts. A direct session gives no such signal, and an integrator who takes a signature as the subject's personal acceptance of a document may accept a delegate's signature without noticing. The subject authorized the delegation by publishing the record, so this is a defaults and documentation matter, not a bypass.
**Recommendation:** State in the `sign` result table that `verificationResult.actor` is non-empty for a delegated signature, that it should equal the `actor` of the sign-in the session key comes from, and that an integrator who needs the identifier's own keys must check `actor === ''`. Consider a stage-3 option that declares whether delegated signatures are acceptable for this request, so the check does not depend on each integrator reading the nested result.

### [SIGN-003] [low] The unsigned metadata slot is returned verbatim inside `verificationResult`
**Location:** `src/api/signing.js:157`, `src/signature.js:405-406`
**Description:** The unsigned metadata slot of the envelope is outside the signed payload (`src/signature.js:294-306`), so the party that seals the response can set it, and so can any other holder of the challenge's `ek`, because the sealing does not authenticate the sender. The `sign` result includes it unchanged as `verificationResult.unsignedMetadata`, next to fields the signature covers. The README `sign` result table describes `verificationResult` as the verified signature and does not single this field out. An integrator who stores or renders fields from `verificationResult` may treat unverified data as verified. The WebAuthn verifier is the only consumer that validates content from this slot, and it does so by checking the `sig` entries against the signed bytes.
**Recommendation:** State in the `sign` result documentation that `unsignedMetadata` is not covered by the signature and is untrusted input, or omit it from the `sign` result once verification completes. The escape-before-render rule in Best Practices also applies to `signedMetadata` values, which the signer controls.

### [SIGN-004] [info] The attachment proof binds names and digests only
**Location:** `src/api/signing.js:113-143`, `src/validator.js:346-365`
**Description:** Stage 3 confirms that the signed attachment list equals the requested list by `name` and `sha256`, and that a signed `sourceUrl`, when present, equals the requested one. The library never fetches an attachment, so it cannot confirm that the file shown to the user has the digest in the challenge. A `sourceUrl` may be a plain `http://` URL on any host, an IPv4 literal included, so the fetched content can be altered in transit, and a descriptor can point the user's browser at an address inside the user's own network. Whether the authenticator fetches such an address is the authenticator's policy. The README states that a verifier must compare the digests with its own copies of the files, and that `sourceUrl` is kept out of the durable proof because it may contain credentials. The challenge includes every `sourceUrl`. It travels sealed under the session key and stays in the application's session store.
**Recommendation:** Add a sentence to the `sign` section that integrators serve attachments over `https` and keep the original files, since the proof is a statement about digests. Avoid presigned or otherwise secret `sourceUrl` values, as the challenge that includes them reaches the authenticator and stays in the session store.

### [SIGN-005] [low] Stage 3 ignores `message`, `attachments`, and `sessionKey` options, and the result does not state the signed message
**Location:** `src/api/signing.js:50-57` and `:148-160`, `src/challenge_response_flow.js:78-85`
**Description:** `_perform` removes `message` and `attachments` from the options before the shared flow checks for unknown options, and it reads them in stage 1 only. At stage 3 a call such as `Triauth.sign({challenge, response, message})` returns `signed:true` for a stored challenge whose `msg` differs from the passed `message`. A non-array `attachments` or a malformed `sessionKey` passes the same way, while a passed `identifier` or `callbackUrl` that differs from the challenge fails with error 401. The documentation says that an `identifier` or `callbackUrl` passed with `challenge` and `response` is verified against the challenge, and an integrator can expect the same of `message`. The result carries the envelope in `result` and the verified fields in `verificationResult`, and neither states the `message` that was signed. `Triauth.verify` needs that `message` as its first argument, so a third party receives a proof without the statement it proves unless the integrator keeps the message next to it. An application that keeps one challenge slot per session and runs two signing flows learns from `signed:true` only that the stored challenge was answered, not which message the user approved.
**Recommendation:** At stage 3, compare a passed `message` with `challenge.data.msg` and a passed `attachments` with `challenge.data.attachments`, and fail with error 401 on a difference, as for `identifier` and `callbackUrl`. Reject a `sessionKey` passed at stage 3 with error 102, or validate it. Return the signed `message` and the matched attachments in the result, next to `result`, so the proof and its statement stay together.

### [SIGN-006] [info] The `result` row of the sign documentation describes the response as received, while `result` is the opened envelope
**Location:** `README.md:1294`, `src/api/signing.js:153`
**Description:** The `result` row of the `sign` result table says the signature is "exactly as received in the `response`". Stage 3 receives a sealed response, opens it with the key of the stored challenge, and returns the opened envelope as `result`. The sealed string and the envelope differ, and only the envelope verifies with `Triauth.verify`. An integrator who stores the `response` parameter as the proof keeps a ciphertext that opens only with the challenge's key.
**Recommendation:** Say that `result` is the signature envelope that the `response` carried, as stage 3 opened it, and that this envelope is the value to store or forward.
