# Fable 5.1 review — Triauth.attest

## Summary

`Triauth.attest` binds every segment of the bundle to the SHA-256 digest of the stored challenge, keeps the user's segment first, pins its identifier and its `via` to the challenge, treats every stated binder as critical on every segment, bounds the segment count by the request, gates attester keys on their `use` option, and returns all or nothing. A DNS failure surfaces as the retryable `dns_unavailable` and never as a verdict. Stage 3 accepts `challenge`, `response` and the two cross-checked options only, so a re-supplied `attestations` option is refused with `invalid_arguments`, and the conformance suite pins it. The request travels sealed under the session key, and the response travels sealed to the key minted with the challenge. The es256 and webauthn-es256 verifiers accept the uncompressed and the compressed P-256 point, and ed25519 keys verify where the runtime supports them. Errors are string codes, with a `reason` on validation errors. The attest unit tests and the attest conformance vectors pass behind the offline zone stub (45 and 257).

The headline concern is the trust anchor of an attester segment. Any identity at the host of a listed provider URL satisfies the attestation, the user included, so a provider URL on the users' own identity domain lets a user mint the attester segment with their own keys (ATTEST-002). The founder accepted this as the relying party's trust decision, with the rule stated in the README and the developer guide. Among the open findings, the one change to make is to add `actor` to the result inspection list, so that a person-bound attestation completed by a delegate is not read as a statement about the subject (ATTEST-004). The one new finding is that stage 3 resolves and verifies every segment of the bundle before it compares the first segment with the challenge identifier and the attester segments with the provider hosts, while the other flows refuse a foreign identifier before any DNS query (ATTEST-008). A probe in the finding confirms it.

The library is safe to use in mission-critical production systems when the integrator follows the documented result inspection. The remaining findings are the device tag and the full attester result in the logs (ATTEST-003), the vacuous success of an empty request (ATTEST-006), and the `http://localhost` carve-out for provider URLs that no attester identity can ever satisfy (ATTEST-007). ATTEST-001 and ATTEST-002 stay as accepted by the founder.

## Findings

### [ATTEST-001] [medium] [reviewed] The request cannot require binders, so unbound attester statements satisfy person-bound claims by default
**Location:** `src/api/attestation.js:336-370` (binder check and matching loop), `src/validator.js:189-235` (`validateAttestations`)
**Description:** An attester segment is accepted when it verifies under an identity at the provider host, its `via` is a listed provider URL, and every binder it states equals the user's value. A segment that states no binder passes. Such a segment proves that the provider's check was completed by someone for this challenge digest. It does not prove that the person was the user named in the challenge. The provider learns only its own URL and the digest, and the authenticator receives the provider's statement as an opaque string in the fragment of its own callback URL (`verifyToken` plus `response`). A user can therefore hand the provider link to another person, let that person complete the check, and open the returned link in their own authenticator session. The resulting bundle verifies with `attested:true`. A relying party that gates an age, identity, or residency decision on `attested:true` alone accepts it. The README asks integrators to inspect `attestations.<id>.signedMetadata.bind` after success, and the trust model places that decision with the application. Nothing in the request or the configuration lets the integrator state the requirement up front, so the safe behaviour depends on application code that runs after the library has already reported success. Anonymous attestations remain the right default for claims such as not-a-robot, so the gap is the absence of an opt-in, not the default itself.
**Recommendation:** Let each requested attestation list the binders it requires, for example `attestations.<id>.bind: ['identifier', 'deviceTag']`, validated at stage 1 (229 on an unrecognized name) and baked into the signed challenge. At stage 3, a segment satisfies that attestation only when its `bind` contains every required binder (the equality rule stays as it is), else 401. Document that `deviceTag` is the strong form, because a provider can learn it only by authenticating the user with triauth, while a typed identifier is unverified. Optionally the authenticator forwards the requirement to the provider as a query parameter. This is the one change to make before launch.
> **Human review (triauthor, 2026-10-01):** By design. Attestations are meant to be as anonymous as possible, and with that level of anonymity comes the fact that by default they are bound to neither an identifier nor a device. The binding is the verification provider's decision. A relying party that needs a person-bound claim chooses a provider whose contract states the binding it applies, and the library enforces that every binder the provider states matches the user. Accepted.

### [ATTEST-002] [medium] [reviewed] Any identity at the provider host satisfies an attestation, so a user whose identity domain hosts the provider URL mints the attester segment with their own keys
**Location:** `src/api/attestation.js:343-358` (matching loop, host-equality rule at line 351), `test/test_attestation.js:186` and `test/fixtures/json/_capture_attest.mjs:878` (self-attestation positive vectors)
**Description:** The attester rule accepts a segment when it is first-party, its `via` is a listed provider URL, and the domain part of its identifier equals the host of that `via`. Every identity published at that host passes. The default key `use` admits the attest flow, so an ordinary device key signs an attester segment. When a relying party lists a provider URL on the users' own identity domain, the user signs the challenge digest a second time with the provider URL as `via` and appends that segment to the bundle. The two segments differ in `via`, so the duplicate-segment guard does not apply. The authenticator UI does not offer this, but the keys are usable by any script at the authenticator origin, and the trust model allows a self-hosted copy. The bundle verifies with `attested:true`, and the provider was never visited. The unit tests and the conformance suite carry this self-attestation as a positive case. On a host that publishes identities for several people, any of those identities signs the segment likewise. The README asks integrators to compare `attestations.<id>.identifier` with the attester the provider documents, so the mitigation runs after success in application code. The previous review rated this low. The rating is now medium because the forgery needs no second party and no provider, and the default accepts it.
**Recommendation:** Refuse a matched attester segment whose identifier equals the user's identifier or actor, by default and without an option. That retires the self-attestation positive vector in the unit tests and in the conformance suite, which is a founder decision. Then let each provider carry an optional expected attester, for example `providers: [{url, attester}]`, enforced at stage 3 with 401, which also closes the second identity at the same host. Until then, state in the README that a provider URL must not sit on a host that publishes identities for the users being attested. This is the one change to make.
> **Human review (triauthor, 2026-10-14):** By design. The trust anchor of an attester segment is the host of the provider URL, and the relying party chooses that host. The README states the rule in the method section (README.md:879). `Triauth.attest` only verifies that a signature came from an identity at the host of one of the listed providers, and it does not interpret what the provider checked. The result inspection list (README.md:1063) asks the integrator to compare `attestations.<id>.identifier` with the attester the provider documents when the provider's host also issues identities to others. The developer guide at https://www.triauth.org/developers/attestations says the same. The provider signs with the keys of its own identity at the domain of the listed address, and the provider list is the relying party's trust decision. A later version may let a request bind a provider to one attester identifier. Accepted.

### [ATTEST-003] [low] Success and debug logs include the device tag and the full attester result
**Location:** `src/api/attestation.js:354` (debug line with the whole matched attester result), `src/api/attestation.js:367` (info line with the user's device tag), `src/challenge_response_flow.js:129` (stage-1 info line with the identifier and the callback URL), `README.md:1917-1919` (Logging warning)
**Description:** The debug line that reports a matched attestation logs the whole attester result, with its keys, its binders and its metadata. When the provider bound the user, that object carries the user's identifier and device tag inside `signedMetadata.bind`. The info line that reports success logs the user's `deviceTag`. Under `mode=private` the device tag embeds the lookup code, which the README classes as a semi-secret that must not reach third parties. Application logs at info level are routinely shipped to third-party log services. Other challenge-response paths emit the same line with the device tag (`src/api/authentication.js:218`, `src/api/authentication.js:616`, `src/api/signing.js:143`), so the exposure is library-wide. The README Logging section warns that the debug level emits protocol artifacts and that the info level logs device tags that can contain a lookup code. The default console logger emits at error level only, which limits the exposure to integrators who raise the level. What remains open is the code side of the recommendation.
**Recommendation:** Log a digest of the device tag, or omit it, at info level, and keep full result objects out of library logs. The Logging section already carries the warning.

### [ATTEST-004] [low] The result inspection guidance omits `actor`, which identifies who stood in front of the provider
**Location:** `README.md:1068-1071`, `src/api/attestation.js:225-228` (the inspection list), `src/api/attestation.js:322-327` (binder targets are the subject's values), `test/fixtures/json/_capture_attest.mjs:1017` (delegated user segment, positive vector)
**Description:** The user segment of an attest bundle may be delegated. The actor's device then runs the authenticator session, opens the provider, and completes the check, under a grant the subject published. The result reports this in `actor`, `actorIdentityDomain` and the composite `deviceTag`. Binders do not distinguish the case, because `bind.identifier` targets the subject and `bind.deviceTag` targets the composite tag. A provider that binds the identifier of the person it actually verified, the actor, fails the bundle with `verification_failed`, while a provider that binds the subject it never saw passes. The conformance suite carries the delegated user segment as a positive vector. The "inspect the result before relying on it" list covers `secure`, `bind` and the attester identifier, but not `actor`. A relying party that follows the list accepts a person-bound attestation completed by the delegate as a statement about the subject.
**Recommendation:** Add `actor` to the inspection list, with the advice to accept a delegated attestation only where the subject's delegate is an acceptable proxy for the claim, and to require `actor === ''` otherwise.

### [ATTEST-006] [info] An empty `attestations` request yields `attested:true` on the user's signature alone
**Location:** `src/validator.js:209` and `src/validator.js:217-234` (an empty object passes every guard and the loop runs over zero entries), `src/api/attestation.js:300` (the signature bound is then one), `src/api/attestation.js:344-365` (the matching loop over zero entries never fails), `test/fixtures/json/_capture_attest.mjs:683` and `test/fixtures/json/_capture_attest.mjs:882` (positive vectors)
**Description:** An empty `attestations` object is valid at stage 1 and at stage 3. The matching loop runs over zero entries, and the result is `attested:true` with an empty `attestations` map. The signature count bound is then one, so the response is an attest-typed signature of the user and nothing else. An integrator who gates a decision on `attested` and builds the request map from a selection that can be empty, grants the decision on a user signature that attests nothing. The validator's own documentation describes the empty object as valid, and a probe confirms that `Validator.validateAttestations({})` is valid. The README section on the method does not mention the case. The conformance suite carries it as a positive vector at both stages.
**Recommendation:** Reject an empty `attestations` object at stage 1 with `invalid_attestations` as the secure default. If the empty request stays supported, state in the README that `attested:true` with an empty map means that the user signed and that no third party attested anything.

### [ATTEST-007] [info] The `http://localhost` carve-out for provider URLs admits a provider that no attester identity can ever satisfy
**Location:** `src/validator.js:242` (provider URLs pass `isSecureUrl`), `src/helpers.js:603-609` (the carve-out), `src/api/attestation.js:352` (the host-equality rule), `src/validator.js:147-151` and `src/helpers.js:688-694` (an identifier domain needs two labels), `test/fixtures/json/_capture_attest.mjs:662` (positive stage-1 vector), `README.md:876` and `README.md:910`
**Description:** Provider URLs are validated with `isSecureUrl`, which accepts `https` URLs on a named host and also `http` URLs whose host is the literal `localhost`. A stage-1 request that lists `http://localhost:8080/verify` as a provider builds a challenge, and the conformance suite pins that as a positive vector. At stage 3 an attester segment matches only when the domain part of its identifier equals the host of its `via`. That host is `localhost`, and `localhost` is not a domain name under the identifier grammar, which requires at least two labels. A probe confirms it. `isDomainName('localhost')` is false, `x@localhost` is an invalid identifier, `isSecureUrl('http://localhost:8080/v')` is true with `urlHost` returning `localhost`, and `validateAttestations` accepts the provider. No identity can exist at that host, so the attester segment cannot be built and the request can never be satisfied. The carve-out widens the accepted set of trust anchors without a use that works. The README describes `providers` as an array of `https://` URL strings. The same carve-out is useful for the callback URL, where the user segment carries the base URL and no identity is involved.
**Recommendation:** Reject `http://localhost` provider URLs at stage 1 with `invalid_attestations`, so the provider grammar is `https` on a named host only, and drop the positive vector. A provider under development can run on a secure origin under a name that resolves locally, as the attester identity needs a domain name in any case.

### [ATTEST-008] [info] Stage 3 resolves and verifies every segment before it compares the segment with the challenge or the provider hosts
**Location:** `src/api/attestation.js:296-301` (the bundle is verified with no `identifier` constraint), `src/api/attestation.js:309` (the first segment is compared with the challenge after verification), `src/api/attestation.js:347-353` (the provider-host rule runs after verification), `src/multi_signature.js:146-154` (every segment is verified in order under the same constraints), `src/signature.js:281-289` and `src/signature.js:320` (an `identifier` constraint is checked before the DNS resolution, which otherwise runs for every segment), `src/challenge_response_flow.js:306-312` (the other flows pass the challenge identifier as a constraint), `README.md:2067-2068` (the rate-limit note)
**Description:** The attest bundle carries the user's segment and attester segments under other identifiers, so the method passes no `identifier` constraint to `response.verify`. Every segment is therefore resolved through DNS and verified first, and only then is the first segment compared with the challenge identifier and each attester segment with the provider hosts. The other flows pass the challenge identifier, and `Signature.verify` refuses a mismatch before any DNS query. A probe against the offline zone stub confirms the difference. An attest response whose first segment names `nobody@unrelated-domain.example` with a bogus signature makes the relying party query the TXT records of that domain before it returns `verification_failed`. The same envelope in the auth flow returns `verification_failed` with no query. A bundle of a valid user segment, three valid attester segments and a fifth segment that names an unrelated domain costs nine lookups and four signature verifications before it fails, and a delegated attester segment also walks the actor's and the subject's records before the matching loop refuses it. The response must be sealed to the `ek` of the stored challenge, so only the user's authenticator can submit one, the request bounds the bundle to five segments, and the README asks for rate limits on stage 3. What remains is that the holder of a challenge chooses which domains the relying party's resolvers query, and that a bundle built to fail costs as much as one built to pass.
**Recommendation:** Parse the envelope before `response.verify` and return `verification_failed` when the first segment's identifier differs from the challenge identifier, when a later segment carries an `actor`, or when the domain of a later segment's identifier is not the host of a requested provider URL. The checks after verification stay as they are. `Response` parses the multi-signature internally, so this is a small refactor of the attest path only.
