# Fable 5.1 review — Triauth.attest

## Summary

`Triauth.attest` binds every segment of the bundle to the digest of the stored challenge, keeps the user's segment first, pins its identifier and its `via` to the challenge, treats every stated binder as critical on every segment, bounds the segment count by the request, gates attester keys on their `use` option, and returns all or nothing. A DNS failure surfaces as a retryable 110 and never as a verdict. The request travels sealed under the session key, and the response travels sealed to the key minted with the challenge. Since the previous review the es256 and webauthn-es256 verifiers also accept a compressed P-256 point, decoded with an on-curve check before import. That change touches key import only and not the verification logic of this method. The attest unit tests and the attest conformance vectors pass behind the offline zone stub (43 and 253).

The headline concern is still the trust anchor of an attester segment. Any identity at the host of a listed provider URL satisfies the attestation, the user included, so a provider URL on the users' own identity domain lets a user mint the attester segment with their own keys (ATTEST-002). The founder accepted this as the relying party's trust decision, with the rule stated in the README and the developer guide. Among the open findings, the one change to make is to compare a re-supplied `attestations` option at stage 3 with the stored challenge and fail with 401 on a difference, as the flow already does for `identifier` and `callbackUrl` (ATTEST-005). Today that option is accepted and dropped without a trace, which the probe in the finding confirms.

The library is safe to use in mission-critical production systems when the integrator follows the documented result inspection. The remaining findings are the device tag and the full attester result in the logs (ATTEST-003), the inspection guidance that omits `actor` (ATTEST-004), the vacuous success of an empty request (ATTEST-006), and the `http://localhost` carve-out for provider URLs that no attester identity can ever satisfy (ATTEST-007). ATTEST-001 and ATTEST-002 stay as accepted by the founder.

## Findings

### [ATTEST-001] [medium] [reviewed] The request cannot require binders, so unbound attester statements satisfy person-bound claims by default
**Location:** `src/api/attestation.js:336-370` (binder check and matching loop), `src/validator.js:189-235` (`validateAttestations`)
**Description:** An attester segment is accepted when it verifies under an identity at the provider host, its `via` is a listed provider URL, and every binder it states equals the user's value. A segment that states no binder passes. Such a segment proves that the provider's check was completed by someone for this challenge digest. It does not prove that the person was the user named in the challenge. The provider learns only its own URL and the digest, and the authenticator receives the provider's statement as an opaque string in the fragment of its own callback URL (`verifyToken` plus `response`). A user can therefore hand the provider link to another person, let that person complete the check, and open the returned link in their own authenticator session. The resulting bundle verifies with `attested:true`. A relying party that gates an age, identity, or residency decision on `attested:true` alone accepts it. The README asks integrators to inspect `attestations.<id>.signedMetadata.bind` after success, and the trust model places that decision with the application. Nothing in the request or the configuration lets the integrator state the requirement up front, so the safe behaviour depends on application code that runs after the library has already reported success. Anonymous attestations remain the right default for claims such as not-a-robot, so the gap is the absence of an opt-in, not the default itself.
**Recommendation:** Let each requested attestation list the binders it requires, for example `attestations.<id>.bind: ['identifier', 'deviceTag']`, validated at stage 1 (229 on an unrecognized name) and baked into the signed challenge. At stage 3, a segment satisfies that attestation only when its `bind` contains every required binder (the equality rule stays as it is), else 401. Document that `deviceTag` is the strong form, because a provider can learn it only by authenticating the user with triauth, while a typed identifier is unverified. Optionally the authenticator forwards the requirement to the provider as a query parameter. This is the one change to make before launch.
> **Human review (triauthor, 2026-10-01):** By design. Attestations are meant to be as anonymous as possible, and with that level of anonymity comes the fact that by default they are bound to neither an identifier nor a device. The binding is the verification provider's decision. A relying party that needs a person-bound claim chooses a provider whose contract states the binding it applies, and the library enforces that every binder the provider states matches the user. Accepted.

### [ATTEST-002] [medium] [reviewed] Any identity at the provider host satisfies an attestation, so a user whose identity domain hosts the provider URL mints the attester segment with their own keys
**Location:** `src/api/attestation.js:343-358` (matching loop, host-equality rule at line 351), `test/test_attestation.js:186` and `test/fixtures/json/_capture_attest.mjs:878` (self-attestation positive vectors)
**Description:** The attester rule accepts a segment when it is first-party, its `via` is a listed provider URL, and the domain part of its identifier equals the host of that `via`. Every identity published at that host passes. The default key `use` admits the attest flow, so an ordinary device key signs an attester segment. When a relying party lists a provider URL on the users' own identity domain, the user signs the challenge digest a second time with the provider URL as `via` and appends that segment to the bundle. The two segments differ in `via`, so the duplicate-segment guard does not apply. The authenticator UI does not offer this, but the keys are usable by any script at the authenticator origin, and the trust model allows a self-hosted copy. The bundle verifies with `attested:true`, and the provider was never visited. The unit tests and the conformance suite carry this self-attestation as a positive case. On a host that publishes identities for several people, any of those identities signs the segment likewise. The README asks integrators to compare `attestations.<id>.identifier` with the attester the provider documents, so the mitigation runs after success in application code. The previous review rated this low. The rating is now medium because the forgery needs no second party and no provider, and the default accepts it.
**Recommendation:** Refuse a matched attester segment whose identifier equals the user's identifier or actor, by default and without an option. That retires the self-attestation positive vector in the unit tests and in the conformance suite, which is a founder decision. Then let each provider carry an optional expected attester, for example `providers: [{url, attester}]`, enforced at stage 3 with 401, which also closes the second identity at the same host. Until then, state in the README that a provider URL must not sit on a host that publishes identities for the users being attested. This is the one change to make.
> **Human review (triauthor, 2026-10-14):** By design. The trust anchor of an attester segment is the host of the provider URL, and the relying party chooses that host. The README states the rule in the method section (README.md:879). `Triauth.attest` only verifies that a signature came from an identity at the host of one of the listed providers, and it does not interpret what the provider checked. The result inspection list (README.md:1063) asks the integrator to compare `attestations.<id>.identifier` with the attester the provider documents when the provider's host also issues identities to others. The developer guide at https://www.triauth.org/developers/attestations says the same. The provider signs with the keys of its own identity at the domain of the listed address, and the provider list is the relying party's trust decision. A later version may let a request bind a provider to one attester identifier. Accepted.

### [ATTEST-003] [low] Success and debug logs include the device tag and the full attester result
**Location:** `src/api/attestation.js:355` (debug line with the whole matched attester result), `src/api/attestation.js:368` (info line with the user's device tag), `src/challenge_response_flow.js:124` (stage-1 info line with the identifier and the callback URL), `README.md:1892-1894` (Logging warning)
**Description:** The debug line that reports a matched attestation logs the whole attester result, with its keys, its binders and its metadata. When the provider bound the user, that object carries the user's identifier and device tag inside `signedMetadata.bind`. The info line that reports success logs the user's `deviceTag`. Under `mode=private` the device tag embeds the lookup code, which the README classes as a semi-secret that must not reach third parties. Application logs at info level are routinely shipped to third-party log services. The same success line exists in the authenticate, ping, sign and stamp paths, so the exposure is library-wide. The README Logging section warns that the debug level emits protocol artifacts and that the info level logs device tags that can contain a lookup code. The default console logger emits at error level only, which limits the exposure to integrators who raise the level. What remains open is the code side of the recommendation.
**Recommendation:** Log a digest of the device tag, or omit it, at info level, and keep full result objects out of library logs. The Logging section already carries the warning.

### [ATTEST-004] [low] The result inspection guidance omits `actor`, which identifies who stood in front of the provider
**Location:** `README.md:1062-1065`, `src/api/attestation.js:225-228`
**Description:** The user segment of an attest bundle may be delegated. The actor's device then runs the authenticator session, opens the provider, and completes the check, under a grant the subject published. The result reports this in `actor`, `actorIdentityDomain` and the composite `deviceTag`. Binders do not distinguish the case, because `bind.identifier` targets the subject and `bind.deviceTag` targets the composite tag. The conformance suite carries the delegated user segment as a positive vector. The "inspect the result before relying on it" list covers `secure`, `bind` and the attester identifier, but not `actor`. A relying party that follows the list accepts a person-bound attestation completed by the delegate as a statement about the subject.
**Recommendation:** Add `actor` to the inspection list, with the advice to accept a delegated attestation only where the subject's delegate is an acceptable proxy for the claim, and to require `actor === ''` otherwise.

### [ATTEST-005] [low] A stage-3 `attestations` option is accepted and ignored, while `identifier` and `callbackUrl` are cross-checked
**Location:** `src/api/attestation.js:273-275` (the option is removed before the flow sees it), `src/api/attestation.js:290-292` (verification reads the challenge only), `src/challenge_response_flow.js:240-246` (stage-3 cross-check of `identifier` and `callbackUrl`), `README.md:961-962`
**Description:** The method removes `attestations` from the options before the flow validates them, and stage 3 reads the requested attestations from the stored challenge only. A caller who passes `attestations` together with `challenge` and `response` gets no error and no comparison. A probe against the offline zone stub confirms it. A stage-3 call with a provider list that differs from the challenge returns `attested:true`, and so does a call with the string `'garbage'` as the option, while a `callbackUrl` that differs from the challenge returns 401. The flow compares a re-supplied `identifier` or `callbackUrl` with the challenge and fails with 401 on a mismatch, and the README documents that check for both. Every other unknown option fails with 102. An integrator who passes the current provider list at stage 3 to pin it, for example after a provider was removed from the trusted set between the two stages, believes the library enforces that list. The library enforces the list baked into the challenge at stage 1. A stale challenge then accepts a provider that the application no longer lists, for as long as the attest window allows, and the caller's intent is silently dropped.
**Recommendation:** Compare a re-supplied `attestations` option with `challenge.data.attest` and fail with 401 on any difference, the way `identifier` and `callbackUrl` are handled. Rejecting the option with 102, as the flow does for every unknown option, is the smaller alternative. Document the chosen behaviour next to the sentence on `identifier` and `callbackUrl`.

### [ATTEST-006] [info] An empty `attestations` request yields `attested:true` on the user's signature alone
**Location:** `src/validator.js:182` and `src/validator.js:189-204` (an empty object passes), `src/api/attestation.js:345-366` (the matching loop over zero entries never fails)
**Description:** An empty `attestations` object is valid at stage 1 and at stage 3. The matching loop runs over zero entries, and the result is `attested:true` with an empty `attestations` map. The signature count bound is then one, so the response is an attest-typed signature of the user and nothing else. An integrator who gates a decision on `attested` and builds the request map from a selection that can be empty, grants the decision on a user signature that attests nothing. The validator's own documentation describes the empty object as valid. The README section on the method does not mention the case. The conformance suite carries it as a positive vector.
**Recommendation:** Reject an empty `attestations` object at stage 1 with 229 as the secure default. If the empty request stays supported, state in the README that `attested:true` with an empty map means that the user signed and that no third party attested anything.

### [ATTEST-007] [info] The `http://localhost` carve-out for provider URLs admits a provider that no attester identity can ever satisfy
**Location:** `src/validator.js:211-215` (provider URLs pass `isSecureUrl`), `src/helpers.js:586-592` (the carve-out), `src/api/attestation.js:353` (the host-equality rule), `src/validator.js:122-126` (an identifier domain needs two labels), `test/fixtures/json/_capture_attest.mjs:659` (positive stage-1 vector), `README.md:870`
**Description:** Provider URLs are validated with `isSecureUrl`, which accepts `https` URLs on a named host and also `http` URLs whose host is the literal `localhost`. A stage-1 request that lists `http://localhost:8080/verify` as a provider builds a challenge, and the conformance suite pins that as a positive vector. At stage 3 an attester segment matches only when the domain part of its identifier equals the host of its `via`. That host is `localhost`, and `localhost` is not a domain name under the identifier grammar, which requires at least two labels. No identity can exist at that host, so the attester segment cannot be built and the request can never be satisfied. The carve-out widens the accepted set of trust anchors without a use that works. The README describes `providers` as an array of `https://` URL strings. The same carve-out is useful for the callback URL, where the user segment carries the base URL and no identity is involved.
**Recommendation:** Reject `http://localhost` provider URLs at stage 1 with 229, so the provider grammar is `https` on a named host only, and drop the positive vector. A provider under development can run on a secure origin under a name that resolves locally, as the attester identity needs a domain name in any case.
