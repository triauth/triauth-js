# Fable 5.1 review — Triauth.verify

## Summary

`Triauth.verify` parses the envelope into at most five segments, checks the caller's constraints before any network or crypto work, resolves each signer through the endpoint record and the identity records, requires every applicable key of one device group to verify the reconstructed payload, enforces the include grant and its scope for delegated segments, and reports a three-state verdict. The signed span binds every envelope field except the unsigned-metadata slot, metadata decoding is bounded and prototype-safe, WebAuthn assertions are tied to the message digest and to the resolved authenticator origin, malformed or mis-optioned keys taint their device group, and a DNS failure is a retryable error rather than a false negative. The headline concern is that every value constraint is opt-in. A `stamp` is minted with no user interaction over text that the token-holding site chooses, and a verifier that does not pin `type` accepts it as an interactive `sign` (VERIFY-001). The one recommendation of this review is to require `constraints.type`, the secure-by-default move already made for `maxSignatures`. The other findings are hardening and documentation items. The library is safe to use in mission-critical production systems for this scope when the integrator pins `type` (plus `via` and a time window where the proof gates anything), reads `secure` or sets `requireSecure`, and rate-limits the endpoint. No finding reaches high or critical. The trust model was read from the local `triauth-www/protocol/trust-model.md` source, as the published page was not reachable from this run.

## Findings

### [VERIFY-001] [medium] [reviewed] All value constraints are opt-in, so a non-interactive stamp verifies as an interactive signature unless the caller pins `type`
**Location:** `src/api/signing.js:667-715` (only `maxSignatures` defaults closed), `src/signature.js:281-289`, `README.md:1637`
**Description:** `Triauth.verify` compares `constraints.type` with the envelope only when the caller supplies it. A `sign` envelope and a `stamp` envelope share the same signed layout and the same free-text `msg` payload, and differ only in the signed `type` slot. A stamp is issued without any user interaction, over any message of up to 2 KB chosen by the application that holds a `stampToken` (`src/api/signing.js:460` states that the authenticator "will immediately respond with the stamp"), whereas a `sign` requires the user to read the message and approve it. The README presents `sign` results as independent, third-party-verifiable proof that a user accepted terms, so third parties are the intended callers of `verify`. A verifier that passes no `type` and does not inspect `result.type` accepts `|stamp;<user>;;<via>;v1;<ts>;;;<sig>|` over "I accept the terms" as `{valid:true}`. Any site the user once granted a stamp token can therefore produce a signed statement in the user's name over arbitrary text and present it to that verifier. Pinning `via` does not close this, because a transferable proof is verified without knowing which site requested it, and the stamp's `via` is the minting site's own base URL. The library already applies the secure-by-default rule to `maxSignatures`, so that a caller checking only `valid` can never silently receive a multi-signature aggregate. The same reasoning applies to the signature type, and the difference here is user consent rather than result shape. The README constraints table describes `type` neutrally ("The type of signature") and the JSDoc says to pin it "when possible". Mitigating factors are that the result exposes `type`, that the attacker needs a stamp token for the victim's device, and that an identity can withhold stamp use from a key through the key record's `use` option.
**Recommendation:** Require `constraints.type` and reject its absence with error 101, as a malformed `maxSignatures` already is. Every documented use of `verify` knows the type it expects (`sign` for consent proofs, `stamp` for presence proofs, `attest` for bundles with `maxSignatures` raised, `auth` or `ping` for re-checking a stored response), so nothing legitimate is lost. If the API is to stay permissive, make `type` pinning a MUST in the README verify section, and spell out the stamp-for-sign substitution there and in the transferable-proof warning of the sign section.
> **Human review (triauthor, 2026-10-01):** By design. `verify` is deliberately flexible, so that one method can check any triauth signature a caller holds. With that flexibility comes the caller's duty to inspect the result with care, `type` included, and to pass the constraints they expect wherever they can. Accepted.

### [VERIFY-002] [low] The duplicate-segment guard is syntactic, so one captured signature can pad a multi-signature count
**Location:** `src/multi_signature.js:76-79`, `src/signature.js:291-304`, `src/identity_keys.js:284-286`, `src/verifiers/ecdsa.js:85-92`
**Description:** `MultiSignature` rejects envelopes with byte-identical segments, and the suite labels this guard as the defense against "a single signature replayed to pad the segment count". Three edits produce a byte-different segment that still verifies under the same key, and none of them needs the private key. The unsigned-metadata slot is by design outside the signed payload, so rewriting `;;` into `;e30;` (the encoding of `{}`) changes the bytes and nothing else. For a multi-key device, the crypto signatures can be reordered, because `IdentityKeys.verify` tries every signature against every key. For `es256` keys, WebCrypto accepts both `(r, s)` and `(r, n-s)`, so a signature can be malleated, while Node's Ed25519 verification rejects a non-canonical `s`, which makes this third route ECDSA-only. A holder of one valid segment can thus build an envelope of two to five segments that satisfies `minSignatures` with no second signature. The documented contract stays accurate, because the README says `minSignatures` counts segments rather than signers and asks callers to check `signatures[].identifier` and `deviceTag`, but the constructor comment and the vector name promise a replay defense that the guard does not deliver, and a caller who relies on it is misled.
**Recommendation:** After the per-segment loop in `MultiSignature.verify`, reject an envelope in which two segments share `(type, identifier, actor, via, deviceTag)`. A legitimate co-signature never needs the same device twice over the same message and `via`, and the attest flow's overlap case reuses one segment for several attestation ids rather than two segments. This changes the two same-signer-twice vectors in `verify.json`. If the current contract is kept, reword the constructor comment and the vector so that they claim only syntactic deduplication. Do not enforce low-S at the verifier, since WebCrypto signers emit high-S signatures half of the time.

### [VERIFY-003] [low] `message` has no size bound and is re-hashed on every verification attempt
**Location:** `src/api/signing.js:676-681`, `src/signature.js:294-306`, `src/identity_keys.js:266-292`, `src/verifiers/ecdsa.js:85-92`, `src/verifiers/web_authn.js:120`
**Description:** The only check on `message` is `typeof message === 'string'`. No genuine triauth signature covers a payload longer than a challenge string, as sign and stamp messages are capped at 2 KB by `validateMessage`, auth and ping sign the challenge of at most 16 KB, and attest signs a 43-character digest, so any longer message can only fail. It is nevertheless concatenated into the payload, scanned for unpaired surrogates and UTF-8 encoded in every `verifier.verify` call, and hashed inside `crypto.subtle.verify` for each key-and-signature attempt, up to 10 devices times 10 crypto signatures per segment, with one more digest per attempt in the WebAuthn verifier. `verify` is the API aimed at endpoints that receive anonymous input, and the DNS lookups for the attacker-chosen identifier precede the crypto, so a large message multiplies the CPU spent per request. The body limit of the host framework usually bounds this, which keeps the severity low.
**Recommendation:** Reject a `message` whose byte size exceeds `LIMITS.challengeBytesize` (or a dedicated limit) with error 101 before any DNS or crypto work.

### [VERIFY-004] [low] The rate-limit guidance omits `Triauth.verify`, the method most exposed to anonymous input
**Location:** `README.md:2041-2042`
**Description:** The Best Practices bullet asks integrators to rate-limit stage 1 and 3 of the challenge-response methods because they resolve a caller-supplied identifier. `verify` resolves the identifiers embedded in the caller-supplied envelope in the same way, two DNS names for a direct segment and four for a delegated one, each through the three resolvers of the default `MultiResolver` with an 8.5 s ceiling, and then runs up to a hundred signature verifications per segment. An attacker who controls the authoritative DNS of the identifier's domain can also make each lookup slow. The `maxSignatures` default of 1 bounds the cost of one call, but a verification endpoint without a rate limit remains a cheap way to tie up request handlers and resolver quota.
**Recommendation:** Add `Triauth.verify` to the rate-limit bullet, and recommend keeping `maxSignatures` at the minimum the use case needs and placing a `CachingResolver` in front of the resolver on verification endpoints.

### [VERIFY-005] [info] No default freshness window, and `signedAt` is the signer's own claim
**Location:** `src/signature.js:273-278`, `README.md:1497`, `README.md:1640-1641`
**Description:** `notBefore` and `notAfter` are applied only when supplied, so by default the envelope timestamp is never compared with the clock. The timestamp is inside the signed span, which makes it tamper-evident, but the signing device chooses it, so on its own it proves nothing about when the signature was made. A stamp over a fixed message such as "logged-in" that is handed to a third party therefore verifies indefinitely while the keys stay published. The sign and stamp sections and the Best Practices explain that these are transferable proofs and that replay protection needs a verifier-chosen nonce in the message, and the Constraints example shows a `notBefore`, but the verify section never states that no window applies by default.
**Recommendation:** State in the verify section that no time window is applied unless `notBefore` or `notAfter` is passed (strict, with no clock-drift allowance), and recommend a window for any time-sensitive decision together with a nonce in `message` for presence proofs. The section heading at `README.md:1497` should also list the `config` argument, which the synopsis omits.
