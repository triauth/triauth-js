# Fable 5.1 review — Triauth.verify

## Summary

`Triauth.verify` parses the envelope into at most five segments, applies the segment-count policy and every value and time constraint before any network or crypto work, resolves each signer through the endpoint record and the identity records, requires every applicable key of one device group to verify the reconstructed payload, enforces the include grant with its `use` and `scope` for delegated segments, and reports a three-state verdict in which DNS failure stays a retryable error. The signed span binds every envelope field except the unsigned-metadata slot, metadata decoding is bounded, canonical and prototype-safe, WebAuthn assertions are tied to the message digest and to the resolved authenticator origin, malformed or mis-optioned keys taint their device group, and the private-mode commitment check closes the truncated-label collision. The reviewed commit decodes compressed P-256 key records in the library itself, so the accepted key forms are the same on every runtime. The decoder requires `x < p`, checks that the recovered `y` squares back to the curve equation, takes the parity from the prefix, and refuses the hybrid form and every other prefix or length. A key that does not decode is skipped, never trusted, and it fails its device group. The decoder costs about 0.07 ms per key, below one ECDSA verification. Seven unit tests and nine conformance vectors cover both prefixes, the negated point, the hybrid form, a prefix outside SEC 1, an `x` of `p` or more, and an `x` with no point on the curve. This review found no issue in it. The verify conformance suite and the internals suites pass on the reviewed commit. The one recommendation of this review is to reject a multi-signature envelope in which two segments name the same signer and device, because one captured signature turns into three byte-different segments that satisfy `minSignatures:3` with no second signature, which this review reproduced on the reviewed commit (VERIFY-002). The other open findings are a missing size bound on `message` with DNS work ahead of the cheap rejects, the rate-limit guidance that omits this method, and two documentation gaps. The library is safe to use in mission-critical production systems for this scope when the integrator pins `type` and `via`, passes a time window where the proof gates anything, checks signer distinctness on multi-signature results, reads `secure` or sets `requireSecure`, and rate-limits the endpoint. No finding reaches high or critical. The trust model was read from the local `triauth-www/protocol/trust-model.md` source.

## Findings

### [VERIFY-001] [medium] [reviewed] All value constraints are opt-in, so a non-interactive stamp verifies as an interactive signature unless the caller pins `type`
**Location:** `src/api/signing.js:667-715` (only `maxSignatures` defaults closed), `src/signature.js:281-289`, `README.md:1637`
**Description:** `Triauth.verify` compares `constraints.type` with the envelope only when the caller supplies it. A `sign` envelope and a `stamp` envelope share the same signed layout and the same free-text `msg` payload, and differ only in the signed `type` slot. A stamp is issued without any user interaction, over any message of up to 2 KB chosen by the application that holds a `stampToken` (`src/api/signing.js:460` states that the authenticator "will immediately respond with the stamp"), whereas a `sign` requires the user to read the message and approve it. The README presents `sign` results as independent, third-party-verifiable proof that a user accepted terms, so third parties are the intended callers of `verify`. A verifier that passes no `type` and does not inspect `result.type` accepts `|stamp;<user>;;<via>;v1;<ts>;;;<sig>|` over "I accept the terms" as `{valid:true}`. Any site the user once granted a stamp token can therefore produce a signed statement in the user's name over arbitrary text and present it to that verifier. Pinning `via` does not close this, because a transferable proof is verified without knowing which site requested it, and the stamp's `via` is the minting site's own base URL. The library already applies the secure-by-default rule to `maxSignatures`, so that a caller checking only `valid` can never silently receive a multi-signature aggregate. The same reasoning applies to the signature type, and the difference here is user consent rather than result shape. The README constraints table describes `type` neutrally ("The type of signature") and the JSDoc says to pin it "when possible". Mitigating factors are that the result exposes `type`, that the attacker needs a stamp token for the victim's device, and that an identity can withhold stamp use from a key through the key record's `use` option.
**Recommendation:** Require `constraints.type` and reject its absence with error 101, as a malformed `maxSignatures` already is. Every documented use of `verify` knows the type it expects (`sign` for consent proofs, `stamp` for presence proofs, `attest` for bundles with `maxSignatures` raised, `auth` or `ping` for re-checking a stored response), so nothing legitimate is lost. If the API is to stay permissive, make `type` pinning a MUST in the README verify section, and spell out the stamp-for-sign substitution there and in the transferable-proof warning of the sign section.
> **Human review (triauthor, 2026-10-01):** By design. `verify` is deliberately flexible, so that one method can check any triauth signature a caller holds. With that flexibility comes the caller's duty to inspect the result with care, `type` included, and to pass the constraints they expect wherever they can. Accepted.

### [VERIFY-002] [low] The duplicate-segment guard is syntactic, so one captured signature can pad a multi-signature count
**Location:** `src/multi_signature.js:76-79`, `src/signature.js:291-306`, `src/identity_keys.js:284-286`, `src/verifiers/ecdsa.js:85-97`
**Description:** `MultiSignature` rejects envelopes with byte-identical segments, and the suite labels this guard as the defense against "a single signature replayed to pad the segment count". Three edits produce a byte-different segment that still verifies under the same key, and none of them needs the private key. The unsigned-metadata slot is by design outside the signed payload, so rewriting `;;` into `;e30;` (the encoding of `{}`) changes the bytes and nothing else. For `es256` keys, WebCrypto accepts both `(r, s)` and `(r, n-s)`, so a signature can be malleated, while Node's Ed25519 verification rejects a non-canonical `s`, which makes this route ECDSA-only. For a multi-key device, the crypto signatures can be reordered, because `IdentityKeys.verify` tries every signature against every key. This review reproduced the first two routes on the reviewed commit with the suite's own stub resolver and records. The single `sign` vector of the conformance suite, its unsigned-slot variant, and its malleated variant each verify alone, pass the byte-identical guard as three distinct segments, and form a three-segment envelope that `Triauth.verify` reports as `{valid:true, type:'multisig'}` under `{minSignatures:3, maxSignatures:3}`, with the same identifier and device tag on every segment. A holder of one valid segment can thus build an envelope of two to five segments that satisfies `minSignatures` with no second signature. The documented contract stays accurate, because the README says `minSignatures` counts segments rather than signers and asks callers to check `signatures[].identifier` and `deviceTag`, and the padded segments do carry the same identifier and device tag. The constructor comment and the vector name nevertheless promise a replay defense that the guard does not deliver, and a port that reproduces the vector inherits the overclaim.
**Recommendation:** After the per-segment loop in `MultiSignature.verify`, reject an envelope in which two segments share `(type, identifier, actor, via, deviceTag)`. A legitimate co-signature never needs the same device twice over the same message and `via`, and the attest flow's overlap case reuses one segment for several attestation ids rather than two segments. This changes the two same-signer-twice vectors in `verify.json`. If the current contract is kept, reword the constructor comment and the vector so that they claim only syntactic deduplication. Do not enforce low-S at the verifier, since WebCrypto signers emit high-S signatures half of the time.

### [VERIFY-003] [low] `message` has no size bound, and the DNS lookups precede the rejects that need no DNS
**Location:** `src/api/signing.js:663-670`, `src/signature.js:294-331`, `src/identity_keys.js:236-291`, `src/verifiers/ecdsa.js:85-97`, `src/verifiers/web_authn.js:133`
**Description:** The only check on `message` is `typeof message === 'string'`. No genuine triauth signature covers a payload longer than a challenge string, as sign and stamp messages are capped at 2 KB by `validateMessage`, auth and ping sign the challenge of at most 16 KB, and attest signs a 43-character digest, so any longer message can only fail. It is nevertheless concatenated into the payload, scanned for unpaired surrogates and UTF-8 encoded in every `verifier.verify` call, and hashed inside `crypto.subtle.verify` for each key-and-signature attempt. The first key of every device group tries every crypto signature before the group is abandoned, so an envelope with the maximal ten signatures against an identity with ten devices costs one hundred hash-and-verify rounds over the full message per segment. With a stub resolver and the two-device fixture identity, a 4 MB message with ten bogus signatures cost twenty rounds and about 150 ms of CPU, so an attacker who publishes ten devices under a domain of their own gets five times that per request, and five times more again with `maxSignatures:5` and segments signed by their own key, because the segment loop stops at the first failing segment but not at valid ones. The compressed-key decoder on the reviewed commit costs about 0.07 ms per key, below one ECDSA verification, so it does not add to this amplification. Two definitive rejects also run after the two DNS lookups instead of before them. A segment with more than `LIMITS.maxKeysPerSignature` crypto signatures is refused in `IdentityKeys.verify`, and a message that is not well-formed UTF-16 fails only inside the verifiers. `verify` is the API aimed at endpoints that receive anonymous input, and the body limit of the host framework usually bounds the message, which keeps the severity low.
**Recommendation:** Before any DNS or crypto work, reject with error 101 a `message` whose byte size exceeds `LIMITS.challengeBytesize` (or a dedicated limit) or that carries an unpaired surrogate, and move the `maxKeysPerSignature` check into the `Signature` constructor so that it fails as 225 at parse time.

### [VERIFY-004] [low] The rate-limit guidance omits `Triauth.verify`, the method most exposed to anonymous input
**Location:** `README.md:2038-2039`
**Description:** The Best Practices bullet asks integrators to rate-limit stage 1 and 3 of the challenge-response methods because they resolve a caller-supplied identifier. `verify` resolves the identifiers embedded in the caller-supplied envelope in the same way, two DNS names for a direct segment and four for a delegated one, each through the three resolvers of the default `MultiResolver` with an 8.5 s ceiling, and then runs up to a hundred signature verifications per segment. Each segment builds its own `Identity` objects, so a multi-signature envelope that repeats one signer resolves that signer once per segment, and an attacker who controls the authoritative DNS of the identifier's domain can make each lookup slow. The `maxSignatures` default of 1 bounds the cost of one call, but a verification endpoint without a rate limit remains a cheap way to tie up request handlers and resolver quota.
**Recommendation:** Add `Triauth.verify` to the rate-limit bullet, and recommend keeping `maxSignatures` at the minimum the use case needs and placing a `CachingResolver` in front of the resolver on verification endpoints.

### [VERIFY-005] [info] No default freshness window, and `signedAt` is the signer's own claim
**Location:** `src/signature.js:273-278`, `README.md:1490`, `README.md:1634-1635`
**Description:** `notBefore` and `notAfter` are applied only when supplied, so by default the envelope timestamp is never compared with the clock. The timestamp is inside the signed span, which makes it tamper-evident, but the signing device chooses it, so on its own it proves nothing about when the signature was made. A stamp over a fixed message such as "logged-in" that is handed to a third party therefore verifies indefinitely while the keys stay published. The sign and stamp sections and the Best Practices explain that these are transferable proofs and that replay protection needs a verifier-chosen nonce in the message, and the Constraints example shows a `notBefore`, but the verify section never states that no window applies by default.
**Recommendation:** State in the verify section that no time window is applied unless `notBefore` or `notAfter` is passed (strict, with no clock-drift allowance), and recommend a window for any time-sensitive decision together with a nonce in `message` for presence proofs. The section heading at `README.md:1490` should also list the `config` argument, which the synopsis omits.

### [VERIFY-006] [info] A non-numeric `notBefore` or `notAfter` is reported as a signature verdict, while the JSDoc promises error 101
**Location:** `src/api/signing.js:643-644`, `src/api/signing.js:677-683`, `src/signature.js:257-265`
**Description:** The JSDoc of `constraints.notBefore` and `constraints.notAfter` says that a non-number is rejected with error 101, and `Triauth.verify` does apply that rule to `minSignatures` and `maxSignatures`. The two time bounds are typed only inside `Signature.verify`, which returns `false`, so `Triauth.verify('m', sig, {notBefore: 'x'})` and `{notAfter: NaN}` return `{valid:false, reason:'invalid'}` on the reviewed commit, with no DNS or crypto work. This fails closed, and the conformance suite pins the behaviour. The caller's own bug is nevertheless reported as a verdict on the signature rather than as an argument error, which is the opposite of the treatment that the same method gives the count bounds, and a caller who logs `reason` to classify failures will file the signature as bad.
**Recommendation:** Validate `notBefore` and `notAfter` next to `minSignatures` and `maxSignatures` in `Triauth.verify` and throw error 101, so that the code matches the JSDoc and a type bug surfaces as `{error}`. If the verdict is preferred, correct the two JSDoc sentences instead, and say in the README rows what a non-number yields.
