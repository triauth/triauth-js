# Fable 5.1 review — Triauth.check

## Summary

`Triauth.check` is a pure DNS liveness re-check. It takes no signature and no user input beyond the stored `identifier` and `deviceTag`. It re-resolves the subject and, for a composite tag, the actor. It answers `valid:true` only when a valid key group with the exact tag digest is still published. For a delegated session the pinned grant tag must still be present on the subject and must reference that actor. Every failure path ends in `valid:false` or `{error}`. The tag lookup is bounded by the resolved identity instance. The `secure` flag is the AND of the endpoint record and every well-formed identity record of both resolutions. The `expires` value is the earliest TTL expiry across the endpoint record, the grant record and the key records. The `requireSecure` option is enforced on the success path only. The private-mode walk re-derives the identity domain from the lookup code carried in the tag and relies on the `commit` binding, so a wrong or rotated code ends the session instead of reading a stranger's records. The 91-case conformance suite pins the security-relevant branches, and all 1469 cases of the JSON suites pass at this commit.

The library is safe to use in mission-critical production systems for this scope. The findings below are hardening and documentation items. CHECK-005 is the one recommendation to act on. The method's contract leaves its error path without a deadline, so a degraded DNS path keeps a revoked device signed in for as long as the degradation lasts. One Best Practices sentence that makes `expires` the deadline for a successful re-check closes it. CHECK-001 remains the code-side item to pick up next.

## Findings

### [CHECK-001] [low] Actor segment of a composite deviceTag selects foreign DNS targets before the grant's ref is compared
**Location:** `src/api/authentication.js:394-397`, `src/identity_includes.js:217-233`
**Description:** For a composite tag, `check` builds an `Identity` from the actor identifier found in the tag and hands it to `IdentityIncludes.find`. The method filters the subject's grants by the pinned tag, then resolves the actor, and compares the grant's `ref` with the actor only after that. A grant tag is derivable from public DNS, because it is the digest of the published `include` record. So any tag of the form `<published grant tag>:<name>@<any-domain>:<anything>` makes the server query `<any-domain>` for its endpoint record, and for its identity domain when the domain is configured, before the ref mismatch returns `valid:false`. Confirmed against an in-memory zone. A tag with the actor segment `someone@attacker.example` produced a query for `attacker.example` under a grant that references `jane@triauthdemo.org`. The exposure needs a tampered tag store, which the README tells integrators to avoid, and stage 1 of the challenge-response methods exposes a comparable lookup surface for arbitrary identifiers. The effect is bounded to outbound DNS lookups chosen by whoever controls the stored tag, so the severity is low.
**Recommendation:** In `IdentityIncludes.find`, drop the candidates whose `domainName` differs from the actor identifier's domain before `actorIdentity.resolve()`, and return `null` when none remains. A ref can only match an actor on the grant's own domain, as both spellings of a ref carry it, so the pre-filter changes no verdict and removes the foreign lookup. Also list `Triauth.check` in the README rate-limiting bullet, since one call performs up to four DNS resolutions.

### [CHECK-002] [low] deviceTag has no closed grammar, so junk suffixes pass, the format check runs after DNS I/O, and malformed tags read as revocations
**Location:** `src/api/authentication.js:342-343`, `src/api/authentication.js:380-392`
**Description:** The tag is parsed with two unbounded `split` calls, and every segment after the first `~` of a component is discarded. Under a public-mode domain the direct tags `<digest>~<code>~junk` and `<digest>~not-a-lookup-code` both validate, and so does `<grant>:<actor>:<digest>~<code>~junk` on the composite path. All three forms are confirmed against an in-memory zone. The composite branch rejects a fourth `:` segment, but no segment is checked against the digest alphabet or length. The composite format check runs only after the subject identity has been resolved, so a malformed tag still costs two DNS queries, and its verdict depends on DNS state (`unresolved` when the subject does not resolve, `revoked` otherwise). A tag that this library can never have minted is reported as `revoked`, while a malformed `identifier` is reported as `{error}`. An integrator who treats `{error}` as "retry later" keeps the session on a permanently invalid identifier and ends it on a corrupted tag. That hides storage or integration defects behind a revocation verdict. None of this is an authentication bypass. A tag that fails the grammar can only lead to `valid:false`.
**Recommendation:** Validate the tag against a closed grammar before any network I/O. A direct tag is a base64url digest of 43 characters with an optional `~` plus exactly 16 uppercase alphanumerics. A composite tag is a `:`-joined triple whose middle segment passes `validateIdentifier` and whose outer segments follow the direct grammar. Report a grammar failure as `{valid:false, reason:'malformed'}`, the shape `Triauth.verify` already uses, so ports and callers can tell corruption from revocation. Add conformance vectors for the extra-`~` forms so a strict port and this implementation cannot drift.

### [CHECK-003] [info] An empty resolver intersection ends every session of the domain for up to one TTL
**Location:** `src/api/authentication.js:347-352`, `src/resolvers/multi_resolver.js:137-150`
**Description:** `check` maps "no `triauth` record" and "no identity records" to `{valid:false, reason:'unresolved'}`, and the README directs integrators to sign the user out on any `valid:false`. Under the default `MultiResolver` a record survives only when every answering resolver carries it. One resolver's empty or truncated answer is enough to empty the intersection without an error, and so is an in-place edit of the apex `triauth` record during the propagation window. The outcome is a domain-wide forced logout rather than a false acceptance, which is the intended fail-closed direction. The README documents the truncating-relay case and its diagnostic probe. Recorded here because the lever is availability-only and sits outside this scope's code.
**Recommendation:** Keep the fail-closed mapping. Consider reporting a resolver disagreement about emptiness (some answers non-empty, intersection empty) as a retryable `{error}` instead of `unresolved`, so a single stale negative answer does not end sessions. Keep the `unresolved` verdict for an agreed empty answer. CHECK-005 bounds how long such an `{error}` may keep a session alive.

### [CHECK-004] [info] README result table documents the single-identity walk only
**Location:** `README.md:524`, `README.md:560-561`
**Description:** The `check` synopsis states that `secure` is true when the domain's `triauth` record and every well-formed record of the identity answer were DNSSEC-validated, and the `reason` row states that `unresolved` means the identifier itself no longer resolves. For a composite tag the code also folds in the actor's endpoint record and identity answer (`identity.secure && actorIdentity.secure`), and it reports `unresolved` when the actor's identity does not resolve. The JSDoc states both and the conformance suite pins both. The README section does not.
**Recommendation:** Add the delegated case to the README `secure` and `reason` rows so the three descriptions stay in lockstep.

### [CHECK-005] [low] The error path has no deadline, so a degraded DNS path suspends revocation for as long as it lasts
**Location:** `src/api/authentication.js:431-432`, `README.md:526`, `README.md:2043-2046`
**Description:** `check` reports `{error}` when the DNS resolution fails, which under the default resolver means that two of its three resolvers failed or the whole query timed out, and, with `requireSecure` set, when the answer was not DNSSEC-validated (error 404). Both paths are confirmed against an in-memory zone. The README defines `{error}` as "status cannot be determined at the moment" and sets no limit on how long a session may continue on repeated errors. The `expires` value is documented as the moment at which re-verification is due, but a re-check that keeps failing past it leaves the session in place. An attacker positioned to degrade the application's own DNS path, for example by blocking its DNS-over-HTTPS egress, or by stripping DNSSEC when `requireSecure` is on, turns every re-check into `{error}` and so keeps a revoked device signed in for the whole duration of the degradation. The lever is interference with the application's egress, not with the user, and the effect prolongs an existing session rather than creating one. The README already sets a hard rule for the sibling case, where a ping that does not return in time counts as a failure.
**Recommendation:** Add a Best Practices bullet, and a sentence in the `check` section, that make `expires` the deadline for a successful re-check. When `check` keeps returning `{error}` past `expires` plus a short grace period, sign the user out, or at least drop elevated privileges, exactly as the README prescribes for a ping that does not return. With that bound in place, the retryable-error direction of CHECK-003 is safe to adopt.

### [CHECK-006] [info] Record caps apply in DNS answer order, so a zone over a cap gets order-dependent verdicts
**Location:** `src/identity_keys.js:97-100`, `src/identity_includes.js:134-137`, `src/resolvers/multi_resolver.js:135`
**Description:** `IdentityKeys.add` ignores a new device once ten groups exist, and `IdentityIncludes.add` ignores a grant once fifty are listed. Both caps apply in the order in which the resolver returns the TXT records, and the `MultiResolver` keeps the order of the first configured resolver that answered. Authoritative servers and resolvers do not promise a stable order. Confirmed against an in-memory zone. An identity with eleven devices gives `valid:true` for the eleventh device's tag when its record leads the answer and `revoked` when it trails, and a fifty-first grant behaves the same way. The verdict can therefore change between two checks of the same tag with no change in the zone. The failure direction is a logout, never a false acceptance, and only zones over the documented caps are affected.
**Recommendation:** Make the caps independent of answer order. Either apply them after sorting (devices by name, grants by tag, which `list()` already sorts by), or treat an identity that exceeds a cap as publishing no valid key groups or grants, so the verdict is a function of the zone content alone. Pin the chosen rule with a conformance vector whose records are listed in both orders, so ports agree.

### [CHECK-007] [info] A stale-serving resolver extends the revocation bound beyond the TTL
**Location:** `src/api/authentication.js:365-373`, `README.md:562`
**Description:** `check` answers `valid:true` whenever every answering resolver still returns the key record, or the grant record, behind the tag. A resolver that serves stale answers while the zone's authoritative servers are unreachable (RFC 8767) keeps returning the pre-revocation record set after its TTL. A revocation made during such an outage, including one that an attacker causes against the authoritative servers, takes effect only once the stale window closes or one resolver stops answering. The intersection narrows the window. A single resolver that answers empty ends the session (CHECK-003), and the default `maxFailures` tolerates a single failed resolver, so the extension needs every answering resolver to serve the stale record. DNSSEC does not shorten it, because the stale signatures stay inside their validity period. The README documents the bound as the TTL alone.
**Recommendation:** State in the `expires` documentation that the TTL bound assumes resolvers that do not serve stale answers, and that the availability of the zone's authoritative DNS is part of the revocation guarantee. No library change.
