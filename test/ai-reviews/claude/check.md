# Fable 5.1 review — Triauth.check

## Summary

`Triauth.check` is a pure DNS liveness re-check. It takes no signature and no user input beyond the stored `identifier` and `deviceTag`. It re-resolves the subject and, for a composite tag, the actor. It answers `valid:true` only when a valid key group with the exact tag digest is still published. For a delegated session the pinned grant tag must still be present on the subject, must pass the subject's `include=` policy, and must reference that actor. Every failure path ends in `valid:false` or `{error}`. The tag lookup is bounded by the resolved identity instance. The `secure` flag is the AND of the endpoint record and every well-formed identity record of both resolutions, and it is computed from the same inputs as the `secure` flag of the sign-in that minted the tag. The `expires` value is the earliest TTL expiry across the endpoint record, the grant record and the key records, again from the same inputs as at sign-in. The `requireSecure` option is enforced on the success path only. The private-mode walk re-derives the identity domain from the lookup code carried in the tag and relies on the `commit` binding, so a wrong or rotated code ends the session instead of reading a stranger's records. Every critical option of a key record and of a grant record is part of the tag preimage, so an edit to either ends the sessions minted under it, which is the fail-closed direction. No path was found on which a revoked device, a revoked grant or a foreign identity yields `valid:true` without a write to the DNS zone or to the application's own tag store, and the trust model places both outside the library. The trust model also places session management with the application, which decides when to re-check, so the contract items below are about what the method tells that application. The 91-case conformance suite pins the security-relevant branches, and all 1581 cases of the JSON suites pass at this commit. Every finding below was re-confirmed against an in-memory zone at this commit.

The library is safe to use in mission-critical production systems for this scope. The findings below are hardening and documentation items. CHECK-005 is the one recommendation to act on. The method's contract leaves its error path without a deadline, so a degraded DNS path keeps a revoked device signed in for as long as the degradation lasts. One Best Practices sentence that makes `expires` the deadline for a successful re-check closes it. CHECK-002 is the code-side item to pick up next: the closed tag grammar lives in `Validator.validateDeviceTag` behind `Triauth.validate`, and one call before the first DNS query puts it in front of `check`.

## Findings

### [CHECK-001] [low] Actor segment of a composite deviceTag selects foreign DNS targets before the grant's ref is compared
**Location:** `src/api/authentication.js:394-397`, `src/identity_includes.js:217-233`
**Description:** For a composite tag, `check` builds an `Identity` from the actor identifier found in the tag and hands it to `IdentityIncludes.find`. The method filters the subject's grants by the pinned tag, then resolves the actor, and compares the grant's `ref` with the actor only after that. A grant tag is derivable from public DNS, because it is the digest of the published `include` record. So any tag of the form `<published grant tag>:<name>@<any-domain>:<anything>` makes the server query `<any-domain>` for its endpoint record, and for its identity domain when the domain is configured, before the ref mismatch returns `valid:false`. Confirmed against an in-memory zone at this commit. A tag with the actor segment `someone@attacker.test` produced queries for `attacker.test` and `someone._at.attacker.test` under a grant that references `jack@other.test`, and the verdict was `revoked`. A tag with an unpublished grant tag produced no actor query. The exposure needs a tampered tag store, which the README tells integrators to avoid, and stage 1 of the challenge-response methods exposes a comparable lookup surface for arbitrary identifiers. The effect is bounded to outbound DNS lookups chosen by whoever controls the stored tag, so the severity is low.
**Recommendation:** In `IdentityIncludes.find`, drop the candidates whose `domainName` differs from the actor identifier's domain before `actorIdentity.resolve()`, and return `null` when none remains. A ref can only match an actor on the grant's own domain, as both spellings of a ref carry it, so the pre-filter changes no verdict and removes the foreign lookup. Also list `Triauth.check` in the README rate-limiting bullet (`README.md:2057-2058`), since one call performs up to four DNS resolutions.

### [CHECK-002] [low] check does not apply the closed deviceTag grammar, so junk suffixes pass, the format check runs after DNS I/O, and malformed tags read as revocations
**Location:** `src/api/authentication.js:337-343`, `src/api/authentication.js:380-392`, `src/validator.js:521-557`, `README.md:1663`
**Description:** The closed grammar of a device tag lives in `Validator.validateDeviceTag`: a 43-character canonical base64url digest with an optional `~` plus a 16-character lookup code, or a `:`-joined triple whose middle segment is an identifier and whose outer segments follow the same rule. `Triauth.validate` exposes it, and the README validate section describes its `deviceTag` input as the tag you pass to `Triauth.check`. `check` itself does not call it. It parses the tag with two unbounded `split` calls and discards every segment after the first `~` of a component. Confirmed against an in-memory zone at this commit. Under a public-mode domain the direct tags `<digest>~ABCDEFGHIJKLMNOP~junk` and `<digest>~not-a-lookup-code` both return `valid:true`, and so does `<grant>:<actor>:<digest>~ABCDEFGHIJKLMNOP~junk` on the composite path, while `Triauth.validate` rejects all three with `invalid_device_tag`. The composite format check runs only after the subject identity has been resolved, so a two-segment tag and a one-megabyte tag of colons each cost the endpoint query and the identity-domain query, and each is written to the info log in full, before the `revoked` verdict. The verdict of a malformed tag depends on DNS state (`unresolved` when the subject does not resolve, `revoked` otherwise). A tag that this library can never have minted is reported as `revoked`, while a malformed `identifier` is reported as `{error}` with the code `invalid_identifier`. An integrator who treats `{error}` as "retry later" keeps the session on a permanently invalid identifier and ends it on a corrupted tag. That hides storage or integration defects behind a revocation verdict. None of this is an authentication bypass. A tag that fails the grammar can only lead to `valid:false`. The validator accepts every tag the library mints, confirmed for a direct tag, a suffixed tag and a composite tag, so a grammar gate in front of `check` changes no verdict for a tag that came from a result.
**Recommendation:** Call `Validator.validateDeviceTag` in `check` right after the type check, before the request-parameters log line and before any network I/O. Report a grammar failure as `{valid:false, reason:'malformed'}`, the shape `Triauth.verify` already uses, so ports and callers can tell corruption from revocation, or report it as the `invalid_device_tag` error in lockstep with the identifier path. Either way, document the chosen shape in the README `reason` row. Add conformance vectors for the extra-`~` forms and the two-segment form, so a strict port and this implementation cannot drift.

### [CHECK-003] [info] An empty resolver intersection ends every session of the domain for up to one TTL
**Location:** `src/api/authentication.js:347-352`, `src/resolvers/multi_resolver.js:137-150`
**Description:** `check` maps "no `triauth` record" and "no identity records" to `{valid:false, reason:'unresolved'}`, and the README directs integrators to sign the user out on any `valid:false`. Under the default `MultiResolver` a record survives only when every answering resolver carries it. One resolver's empty or truncated answer is enough to empty the intersection without an error, and so is an in-place edit of the apex `triauth` record during the propagation window. Confirmed against an in-memory zone at this commit: a two-member `MultiResolver` with `maxFailures:1`, in which one member answers the identity domain in full and the other answers it empty, returns `unresolved` for a published device. The outcome is a domain-wide forced logout rather than a false acceptance, which is the intended fail-closed direction. The README documents the truncating-relay case and its diagnostic probe (`README.md:2086-2092`). Recorded here because the lever is availability-only and sits outside this scope's code.
**Recommendation:** Keep the fail-closed mapping. Consider reporting a resolver disagreement about emptiness (some answers non-empty, intersection empty) as a retryable `{error}` instead of `unresolved`, so a single stale negative answer does not end sessions. Keep the `unresolved` verdict for an agreed empty answer. CHECK-005 bounds how long such an `{error}` may keep a session alive.

### [CHECK-004] [info] README result table documents the single-identity walk only
**Location:** `README.md:524`, `README.md:559-561`
**Description:** The `check` synopsis states that `secure` is true when the domain's `triauth` record and every well-formed record of the identity answer were DNSSEC-validated, and the `reason` row states that `unresolved` means the identifier itself no longer resolves. For a composite tag the code also folds in the actor's endpoint record and identity answer (`identity.secure && actorIdentity.secure`), and it reports `unresolved` when the actor's identity does not resolve. The JSDoc states both and the conformance suite pins both. The README section does not.
**Recommendation:** Add the delegated case to the README `secure` and `reason` rows so the three descriptions stay in lockstep.

### [CHECK-005] [low] The error path has no deadline, so a degraded DNS path suspends revocation for as long as it lasts
**Location:** `src/api/authentication.js:422`, `src/api/authentication.js:431-432`, `README.md:526`, `README.md:2046-2050`, `README.md:2064-2067`
**Description:** `check` reports `{error}` when the DNS resolution fails, which under the default resolver means that two of its three resolvers failed or the whole query timed out, and, with `requireSecure` set, when the answer was not DNSSEC-validated (the error `dnssec_required`). Both paths are confirmed against an in-memory zone at this commit. The README defines `{error}` as "status cannot be determined at the moment" and sets no limit on how long a session may continue on repeated errors. The `expires` value is documented as the moment at which re-verification is due, but a re-check that keeps failing past it leaves the session in place. The trust model states that the application decides when to re-check, so this deadline can only come from the contract the README gives that application. An attacker positioned to degrade the application's own DNS path, for example by blocking its DNS-over-HTTPS egress, or by stripping DNSSEC when `requireSecure` is on, turns every re-check into `{error}` and so keeps a revoked device signed in for the whole duration of the degradation. The lever is interference with the application's egress, not with the user, and the effect prolongs an existing session rather than creating one. The README already sets a hard rule for the sibling case, where a ping that does not return in time counts as a failure.
**Recommendation:** Add a Best Practices bullet, and a sentence in the `check` section, that make `expires` the deadline for a successful re-check. When `check` keeps returning `{error}` past `expires` plus a short grace period, sign the user out, or at least drop elevated privileges, exactly as the README prescribes for a ping that does not return. With that bound in place, the retryable-error direction of CHECK-003 is safe to adopt. A narrower code-side option for the `requireSecure` case is to report a non-validated answer as `{valid:false}` rather than as `{error}`, because under that option a non-DNSSEC answer is a definitive policy outcome and not a transient one. That changes the documented contract of `requireSecure` for this method, so it is a decision to record either way.

### [CHECK-006] [info] Record caps apply in DNS answer order, so a zone over a cap gets order-dependent verdicts and group lists
**Location:** `src/identity_keys.js:97-100`, `src/identity_includes.js:134-137`, `src/identity.js:184-206`, `src/resolvers/multi_resolver.js:135`
**Description:** `IdentityKeys.add` ignores a new device once ten groups exist, `IdentityIncludes.add` ignores a grant once fifty are listed, and the `groups` loop stops taking names once two hundred are collected. All three caps apply in the order in which the resolver returns the TXT records, and the `MultiResolver` keeps the order of the first configured resolver that answered. Authoritative servers and resolvers do not promise a stable order. Confirmed against an in-memory zone at this commit. An identity with eleven devices gives `valid:true` for the eleventh device's tag when its record leads the answer and `revoked` when it trails. A tainted device record counts toward the device cap too, so ten well-formed devices next to one malformed record give `valid:true` for the tenth device when the malformed record trails and `revoked` when it leads. An identity with 201 group names across two records reports a different 200-name list for each record order, so the name that drops out of the authorization input changes between two checks of an unchanged zone. A dropped name is a lost privilege under an allow-list and a lost restriction under a deny-list such as a "suspended" group. The verdict can therefore change between two checks of the same tag with no change in the zone. The key-group direction is a logout, never a false acceptance, and only zones over the documented caps are affected.
**Recommendation:** Make the caps independent of answer order. Either apply them after sorting (devices by name, grants by tag, which `list()` already sorts by, group names lexically), or treat an identity that exceeds a cap as publishing no valid key groups, grants or groups, so the verdict is a function of the zone content alone. Pin the chosen rule with a conformance vector whose records are listed in both orders, so ports agree.

### [CHECK-007] [info] A stale-serving resolver extends the revocation bound beyond the TTL
**Location:** `src/api/authentication.js:365-373`, `README.md:562`
**Description:** `check` answers `valid:true` whenever every answering resolver still returns the key record, or the grant record, behind the tag. A resolver that serves stale answers while the zone's authoritative servers are unreachable (RFC 8767) keeps returning the pre-revocation record set after its TTL. A revocation made during such an outage, including one that an attacker causes against the authoritative servers, takes effect only once the stale window closes or one resolver stops answering. The intersection narrows the window. A single resolver that answers empty ends the session (CHECK-003), and the default `maxFailures` tolerates a single failed resolver, so the extension needs every answering resolver to serve the stale record. DNSSEC does not shorten it, because the stale signatures stay inside their validity period. The README documents the bound as the TTL alone.
**Recommendation:** State in the `expires` documentation that the TTL bound assumes resolvers that do not serve stale answers, and that the availability of the zone's authoritative DNS is part of the revocation guarantee. No library change.

### [CHECK-008] [info] expires is derived from the key, grant and endpoint records only, so the groups it returns are covered by the RRset TTL rule rather than by the code
**Location:** `src/api/authentication.js:373`, `src/api/authentication.js:413-416`, `src/identity.js:168`, `src/identity.js:184-206`, `README.md:562`
**Description:** The `expires` value folds the TTL expiry of the endpoint record, of the matched device's key records and, for a composite tag, of the grant record and the actor's records. The `groups` records and the private-mode `commit` record are read in the same loop, and their per-record expiry is computed at `src/identity.js:168`, but it is not folded into the result. The README `expires` row promises freshness of "the DNS records behind this result", and the JSDoc promises that membership changes take effect within the same bound as key revocation. In real DNS the groups records, the commit record and the key records of one identity sit at one name and so form one RRset, and RFC 2181 gives an RRset a single TTL, so a compliant resolver returns the same TTL for all of them and the promise holds. The code does not enforce it. The conformance stub and the `MultiResolver` carry a TTL per record, and a zone that serves per-record TTLs through a non-normalizing path gave `expires` = now + 1800 s for a groups record with a 60 s TTL next to a 1800 s key record, confirmed against an in-memory zone at this commit. The exposure is a group removal noticed up to the key TTL late, which is stale privilege and never a false `valid`. For the commit record the direction is a logout. A port that folds every consumed record, or a resolver that reports remaining per-record TTLs, would diverge from this implementation on `expires` without a vector to catch it.
**Recommendation:** Track the earliest expiry of every record the result depends on in `Identity.resolve` and fold it into `expires` in `check` with `Helpers.earliest`, so the promise in the `expires` row holds by construction and not by the resolver's RRset handling. Pin it with a conformance vector that gives a groups record a shorter TTL than the key record and expects the shorter expiry.

### [CHECK-009] [info] The request-parameters log line carries the deviceTag, with its lookup codes, before any validation
**Location:** `src/api/authentication.js:335`, `README.md:1911-1913`, `README.md:2060-2062`
**Description:** `check` logs `identifier` and `deviceTag` at the `info` level before the type check and before any grammar check. Under `mode=private` the tag carries the subject's and, for a composite tag, the actor's lookup code as `~` suffixes. The README tells integrators to treat `deviceTag` and both lookup codes like the identifier and never to display them, because the code and the identifier together let anyone read the identity's records, and the README Logging section warns that `info` lines carry identifiers and device tags with their lookup codes. The default logger runs at the `error` level, so nothing is written until an integrator raises the level to `info` or plugs a custom logger, which production request tracing commonly does. From then on every check writes the identifier and the lookup code into the log store, which places the record-reading capability with everyone who has log access. The tag is also logged unvalidated and unbounded. The Node console escapes control characters inside inspected objects, but a logger that prints raw strings receives newlines and escape sequences from a corrupted tag store verbatim. Confirmed against an in-memory zone at this commit: a tag carrying a line feed and an ESC byte reached a capturing logger's `info` method unchanged, and a one-megabyte tag was logged in full. The success-path log lines of `authenticate` and `ping` carry the `deviceTag` too, so the pattern is library-wide.
**Recommendation:** Log the tag with its `~<code>` suffixes redacted, or log a short digest of the tag, and move the line after the type check and after the grammar gate of CHECK-002, so only a well-formed tag is ever written. The README Logging warning covers the documentation side.
